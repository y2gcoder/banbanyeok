# ADR-0011: 혼자 입력한 결과로 사다리 방을 만들 때 방장이 다른 사람 칸을 대신 넣는다

- 상태: proposed (#227, 운영자 확인 대기)
- 더하는 결정: [ADR-0006](0006-favor-draw.md)(서버가 뽑아 방에 저장한다). [ADR-0007](0007-stop-new-hidden-origins.md)(새로 숨기지 않는다)을 따른다.
- 조사: [#227 조사 댓글](https://github.com/y2gcoder/banbanyeok/issues/227#issuecomment-7189816243)

한 사람이 모두의 출발역을 넣어 본 결과에서도 사다리로 "누구 쪽으로" 배려할지 정하고 싶다는 피드백이 있었다. 지금까지 방에는 각자 자기 칸만
넣었고, 혼자 입력한 값은 서버에 저장하지 않았다(공유 링크 주소에만 있다).

검토한 선택지:

- 공유 링크(`/s`)에 뽑은 결과를 싣기: 받은 사람이 '기준 바꿔 보기' 탭에서 아무나 고를 수 있어 뽑기 결과에 힘이 없다. 저장이 없으니 다시 뽑기를
  한 번으로 막을 수도 없다.
- 기존 참여 API로 방장 기기가 친구 칸을 대신 참여시키기: 계약은 그대로지만 서버가 대신 넣은 칸을 구별하지 못한다. 화면 표시와 처리방침
  설명, 참여 통계가 어긋나고, 칸마다 요청이 따로라 일부만 생길 수 있다.

결정:

- 채운 사다리 방은 새 경로 `POST /v1/draw-rooms`로 만든다. 요청은 `host`, `others`(방장이 대신 넣는 칸, 1~3명), `hostPosition`(입력
  순서에서 방장의 자리), 약속일·시간대이고, 방은 늘 favor·draw다. `POST /v1/rooms`는 main과 같다(`others`를 받지 않는다). 방과 모든 칸을
  한 트랜잭션에 넣는다. 입장 시각을 입력 순서대로 1마이크로초씩 늦춰, 표시 이름의 번호와 뽑기 칸 순서가 원래 입력 순서를 따른다.
- 경로를 나눈 이유: 옛 서버는 모르는 필드를 무시하므로, 같은 `/rooms`에 `others`를 실으면 옛 서버가 다른 사람 칸을 버린 방장만의 열린
  방을 201로 만든다. 만든 뒤 조회해 보고 지우는 방법은 조회·삭제가 실패하거나 서버 판이 섞이면 틀린 방이 남거나 지웠다고 잘못 알린다.
  새 경로는 옛 서버에 없으므로 404로 거절되고 아무것도 쓰지 않는다(main 빌드 서버로 확인). 웹은 404·405를 "지금은 만들 수 없다"로만
  알린다. 다른 사람의 출발역을 저장하는 목적은 뽑기에 묶어 둔다. `others`가 비면 400 `INVALID_OTHERS`, 숨긴 칸은 `HIDE_NOT_AVAILABLE`이다.
- 대신 넣은 칸은 `participants.entered_by_host`가 true이고, 응답 `Participant.enteredByHost`로 화면에 "방장이 입력"을 보인다. 그 칸의
  토큰은 만들어 해시만 저장하고 버린다. 본인이 고치거나 지울 수 없고, 방장의 내보내기와 방 삭제로만 지워진다.
- 이런 방은 잠긴 채 시작한다(`locked`). 링크를 받은 사람이 이미 목록에 있는 자기 칸과 겹치게 새로 들어오지 않게 하려는 것이다. 방장은
  지금처럼 풀 수 있고, 풀어서 들어온 사람은 ADR-0006대로 '뽑기 뒤에 들어옴'이다.
- 웹은 혼자 입력한 결과 화면(만든 사람)에서만 진입점을 둔다. 확인 대화상자에서 저장되는 것, 방 링크로 보이는 것, 보관 기간을 알리고 "나"를
  고르게 한 뒤에만 방을 만든다. 결과의 구분은 방의 약속 칸으로 옮긴다. 평일은 시간대만 두고, 토요일·일요일·공휴일은 그 요일 유형이 되는
  가장 가까운 날을 약속일로 둔다(방은 날짜가 없으면 평일로 계산하기 때문이다).
- 웹은 만든 응답을 받은 그 자리에서(조회·이동보다 먼저) 방장 토큰을 기기에 저장한다. 저장하지 못하면(사전 검사는 통과했지만 실제 기록에서
  저장 공간 부족 등) 방으로 가지 않는다. 가면 방장 권한을 잃어
  다른 사람의 정보가 든 방을 지울 수 없다. 대화상자가 받은 토큰을 들고 다시 저장하거나 그 토큰으로 방을 지우게 하고, 그동안 닫거나 새 방을
  만들지 못하게 한다. 삭제는 서버가 지웠다고 답한 때(204, 이미 없는 404)만 끝난 것으로 보고, 실패하면 토큰·키·복구 상태를 그대로 둔다.
  지운 뒤에는 새 `Idempotency-Key`로 만든다(지운 방을 같은 키로 다시 받지 않게).
- 링크를 받은 사람의 "방장이 모두의 출발역을 넣었어요" 안내는 지금 명단의 방장 아닌 사람이 모두 대신 넣은 칸일 때만 보인다. 잠금을 풀어
  직접 들어온 사람이 있으면 일반 잠긴 방 안내다.
- 뽑기 규칙, 공평 순위, 배려 상한, 미리보기는 바꾸지 않는다.

트레이드오프:

- 보내기 전에 방을 새로 만들어 다시 뽑는 것은 막지 못한다. 방마다 다시 뽑기 한 번, 보낸 뒤의 다시 뽑기는 모두에게 보인다는 것까지만
  보장한다. 지금의 각자 입력 방도 같다.
- 대신 넣은 칸을 본인과 잇는 기능(이어받기)과 방장의 대신 고치기는 첫 판에 넣지 않았다. 틀린 칸은 방장이 빼거나 방을 다시 만든다.
- 주말·공휴일 구분의 약속일은 사용자가 고른 날이 아니라 가장 가까운 날이다. 방은 그 다음 날 사라진다(확인 화면에 날짜를 적는다).
- 배포는 서버 → 웹 순서다(`deploy:web-first` 금지). 되돌릴 때는 웹을 먼저(또는 함께) 되돌리고 서버만 단독으로 되돌리지 않는다. 순서가
  깨져도(배포 중간, 브라우저에 남은 새 번들, 서버 판이 섞인 요청) 틀린 방은 생기지 않는다: 옛 서버로 간 만들기는 404로 끝나고, 사용자는
  "지금은 만들 수 없어요"만 본다. 새 서버가 만든 방을 옛 서버가 보여 주면 '방장이 입력' 표시만 빠진다(쓰기는 없음).
- 응답을 잃은 뒤의 복구: 웹은 요청을 보내기 전에 재시도 키와 복구 키(임의 값)를 이 기기(`bby.draw-room.attempt`, 입력은 해시만)에
  저장한다. 서버는 복구 키의 HMAC만 방에 둔다(`rooms.recovery_hash`, 토큰 해시와 같은 키). 만든 뒤 24시간 안에 같은 복구 키가 오면 탭·
  인스턴스와 상관없이 새 방을 만들지 않고 그 방의 방장 토큰과 방장 참여자 토큰을 새로 발급한다(앞 토큰은 무효). 그래서 응답을 잃었거나
  응답 전에 탭이 닫혀도, 같은 기기에서 같은 입력으로 다시 누르면 같은 방의 방장이 된다. 사용자 확인 전에는 아무것도 쓰지 않고, 키는 만든
  기기만 알아 방 접근 범위가 넓어지지 않는다. 키를 저장하지 못하는 브라우저에서는 방을 만들지 않는다. 만료·삭제된 방이나 24시간이 지난
  키는 새 방을 만들고 키를 새 방으로 옮긴다. 복구는 방 만들기 건수에 세지 않는다.
- 남는 한계: 같은 기기가 다시 시도하지 않으면(다른 기기로 옮기거나, 다시 열지 않거나, 다른 사람을 '나'로 고르거나, 브라우저 데이터를
  지움) 응답을 잃은 방은 방장 없이 보관 규칙대로 만료될 때까지 남는다. 저장 매체가 막혀 복구 안내가 뜬 뒤 탭을 닫아도 같다. 이 방을 더
  일찍 지우려면(예: 방장이 처음 들어오기 전까지는 짧게 보관) 보관 규칙을 바꿔야 해 운영자 결정으로 남겼다.
- 같은 `Idempotency-Key`의 재시도는 인스턴스 메모리 캐시로만 같은 방을 돌려준다(방 만들기 전체와 같다). 다른 인스턴스로 간 재시도는 방을
  하나 더 만들 수 있지만, 칸이 반쯤만 생기는 일은 없다.
