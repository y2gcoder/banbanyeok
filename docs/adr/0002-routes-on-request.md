# ADR-0002: 사람별 경로는 저장하지 않고 요청 때 다시 계산하고, 화면에는 '최단 + 2분 안에서 환승이 가장 적은 길'을 보인다

- 상태: 채택 (2026-11-23, #120)
- 바꾼 결정: #120 첫 검토(2026-11-23)의 "보류: 파이프라인은 경로를 저장하지 않는다"

## 맥락

'자세히'의 사람별 시간 막대를 노선 색 구간 + 환승 구간 + 환승역 이름으로 그리려면 사람마다 경로(탄 노선 순서와 갈아탄 역)가 있어야 한다.
od.bin은 칸마다 시간·환승 수만 있고 경로가 없다. 실측(#120 보고서, 2026-11-23)에서 두 방식을 비교했다.

| | 저장 (경로 표, 구분별) | 요청 때 계산 (그래프) |
|---|---|---|
| 산출물 | 환승역·노선만 8구분 4.5MB(공유 사전 1.35MB), 구간 시간까지 12.4MB | 그래프 약 22KB(구분별 대기표 포함) |
| 서버 메모리 | +7~15MB | 거의 0 |
| 요청당 | 표 조회 µs | 사람마다 0.1~1ms |
| 시간이 od와 어긋날 위험 | 따로 만든 표라 있음 | 같은 그래프·같은 코드 + 발행 게이트로 0 |

카카오맵 대조(28쌍)에서 어긋난 4건 가운데 3건은 우리가 몇십 초~2분 빠르다는 이유로 환승이 더 많은 길을 고른 경우였다. 우리 대기는
배차/2 평균이라 1~2분 차이는 모델 오차 안이다.

## 결정

1. **경로는 저장하지 않는다.** 파이프라인은 od.bin을 만든 그래프를 `rg.bin`(data-format §11)으로 발행하고, 서버는 추천 응답의 후보
   (상위 3곳)마다 사람별 경로를 그 자리에서 계산한다. 최단 경로 계산은 `shared:core`의 `RouteSearch` 하나를 파이프라인 발행 게이트와
   서버가 함께 쓴다. 게이트는 산출물 바이트로 다시 계산한 (시간, 환승)이 **모든 구분·모든 칸**에서 od.bin과 같을 때만 발행한다.
2. **화면의 경로는 표시 전용 규칙으로 고른다:** 최단 시간보다 120초(`DISPLAY_ROUTE_SLACK_SECONDS`, 한 곳) 이내로 더 걸리는 경로 가운데
   환승이 가장 적은 것, 같은 환승 수면 더 빠른 것, 그다음 결정적 동률 규칙. **공평 순위(minimax)와 사람별 시간·환승 수(od 값)는 이 규칙과
   상관없이 그대로다.**
3. 구간 시간은 숫자로 보이지 않는다(막대 길이 비율에만). 공유 썸네일에는 넣지 않는다. 경로를 모르면(그래프 없음·읽는 중·계산 실패)
   중립색 막대로 그린다. 출발역을 숨긴 사람의 경로는 그 사람 본인 요청에만 넣는다(경로의 첫 역이 곧 출발역이다).

## 결과

- 산출물은 약 22KB 늘고 manifest가 4세대가 된다(옛 서버는 3세대를 읽는다).
- 화면의 경로와 사람별 '환승 N번'(od 값)이 다를 수 있다(최단보다 느리지만 환승이 적은 길을 보일 때, 모든 구분·칸의 약 8.6%(85,473 / 995,172)가
  최단 경로와 다른 경로를 보인다).
- 규칙을 바꾸려면 상수 하나와 이 ADR을 고친다. 데이터를 다시 발행할 필요는 없다(서버 코드만 바뀐다).
