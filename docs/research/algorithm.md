# 반반역 추천 알고리즘

## 결론 / 권고

- **fair:** `(최장 시간, 최장−최단 차이, 전체 합계, 역 ID)` 오름차순. 기본 동점 허용오차는 **0분**으로 엄밀한 minimax를 지킨다. `[70,70]`보다 `[30,40]`이 먼저다.
- **fast:** `(전체 합계, 최장 시간, 역 ID)` 오름차순.
- **favor:p:** 먼저 엄밀한 fair 1위 `b`를 구한다. 다른 사람 `i`마다 `T[i,c] ≤ T[i,b] + min(15분, T[i,b]×50%)`인 후보만 남긴다. 그 안에서 `(p의 시간, 최장, 차이, 합계, 역 ID)` 오름차순. 상한에는 허용오차를 적용하지 않는다.
- **3분 허용오차는 실험 옵션**으로 제공한다. 기본값을 바꾸려면 사용자 검증이 필요하다. 쌍별 비교 대신 최솟값 기준 밴드를 사용해 순위를 재현한다.
- 환승 보행·대기 등 **실제 이동시간은 시간 행렬에 포함**, 환승 횟수는 별도로 보여준다. 주관적인 환승 벌점을 추가로 합산하지 않는다.
- 막차는 정적 시간 행렬에서 추정하지 않는다. 날짜별 열차 시간표와 환승 가능 여부로 **집 방향 최종 도착이 가능한 마지막 출발**을 계산한다. 이번 프로토타입은 막차 계산을 구현하지 않으며 아래에 필요한 데이터와 계산 방법을 명세한다.
- Python 표준 라이브러리만 사용하는 프로토타입이 3개 노선·18개 역의 다익스트라 행렬과 모드별 추천을 출력한다. **골든 시나리오 16/16, unittest 6/6 통과**(2026-11-12, Python 3.15.2).

이 문서의 순위·상한·문구·버퍼는 제품 설계 **제안**이다. 실제 수도권 운행시간이나 서비스 성능을 측정했다는 뜻이 아니다. 요구사항 출처: [공통 브리프](../00-brief.md), 확인일 2026-11-12. 실행 확인 출처: 아래 명령 및 [소스](../../prototype/algorithm.py), [골든 입력](../../prototype/scenarios.json), [검증 코드](../../prototype/test_algorithm.py).

## 입력과 출력 계약

외부 입력은 다음 구조를 권고한다. 순위 함수에는 `origins`에서 추출한 참가자 ID를 `participants`로, 사전 계산에서 추출한 두 행렬을 전달한다. 출발역은 중복될 수 있지만 참가자 ID는 중복될 수 없다.

```json
{
  "origins": [{"personId":"A","stationId":"R1"}, {"personId":"B","stationId":"B7"}],
  "candidates": ["X", "B4"],
  "times": [[10,20],[24,18]],
  "transfers": [[0,1],[0,0]],
  "mode": "fair",
  "tolerance": 0
}
```

| 항목 | 규칙 |
|---|---|
| 출발지 | 2~4명. 역 ID는 노선별 승강장 ID를 묶는 공통 역 ID. 참가자 ID와 역 ID를 구별 |
| candidates | 추천 가능한 후보역 목록. 중복 금지. 전체 역 대신 기획에서 정한 후보만 순위화 |
| times | N×C 행렬. 행은 참가자 입력 순서, 열은 후보 입력 순서. 출발역→후보역 방향의 분 값. 0 이상 유한 실수 허용 |
| transfers | 같은 N×C 크기. 해당 **최단 시간 경로**의 환승 횟수, 0 이상 정수. 시간 동률 경로 중 최소 환승 |
| 도달 불가 | 두 행렬의 같은 칸을 모두 `null`. 한 명이라도 도달 불가인 후보는 제외. 음수·NaN·무한대·짝이 안 맞는 null은 오류 |
| mode | `fair`, `fast`, `favor:<personId>`. 존재하지 않는 사람과 알 수 없는 모드는 오류 |
| tolerance | 기본 0. 모든 시간 기준에 같은 폭을 적용. 합계 기준의 단위는 사람·분이며 합계에도 폭 3을 그대로 적용 |
| 버전 | 실제 시스템은 행렬 생성시각·데이터 버전·시간대 모델을 함께 관리해야 한다. 프로토타입 함수 인자는 아님 |

출력은 `status`, `mode`, `participants`, `toleranceMinutes`, `baselineStationId`, `favorCaps`, `recommendations`, `excluded`다. 각 추천은 `stationId`, `rank`(1부터 연속), 참가자별 `times`와 `transfers`, `maxMinutes`, `spreadMinutes`, `totalMinutes`, `reasonCode`, `reason`을 가진다. favor는 `favoredMinutes`도 반환한다. ID의 정렬은 로케일 정렬이 아닌 코드포인트 사전순으로 고정한다. 참가자 순서는 입력과 같다.

후보가 비었거나 공통 도달 후보가 없으면 `status=no_common_candidate`, `recommendations=[]`로 반환한다. 후보 제외 이유는 `UNREACHABLE` 또는 `FAVOR_CAP_EXCEEDED`다. 숫자를 임의로 메우지 않는다. 잘못된 입력은 빈 추천과 구별하여 오류로 처리한다(프로토타입은 `ValueError`).

## 순위 계산과 동점

후보 `c`에 대해 `M(c)=max_i T[i,c]`, `D(c)=max_i T[i,c]−min_i T[i,c]`, `S(c)=sum_i T[i,c]`로 정의한다. 차이만 최소화하면 `[70,70]`이 `[30,40]`을 이기는 문제가 생기므로 fair의 첫 기준은 반드시 M이다. N명에서도 같은 정의를 쓴다.

기본값 0분에서는 위 요약의 튜플을 사전식 비교한다. 반올림 전 값으로 순위를 정하고 표시할 때만 반올림한다. 마지막 ID 기준은 입력 후보 순서를 바꿔도 결과를 같게 만든다. 환승 횟수는 동점 기준에도 끼워 넣지 않는다.

3분 옵션을 켜면 기준별로 다음 절차를 적용한다.

1. 현재 집합에서 첫 기준 최솟값 `m`을 구한다.
2. `[m, m+3]`에 속하는 후보를 첫 밴드로 묶는다(경계 포함).
3. 그 밴드 안에서 다음 기준으로 같은 과정을 재귀적으로 반복한다. 기준이 없으면 ID순이다.
4. 첫 밴드에 포함되지 않은 후보들로 돌아가 새 최솟값 기준의 다음 밴드를 만든다.

`abs(a−b)≤3`를 정렬 비교자로 쓰지 않는다. 40≈42, 42≈44여도 40과 44는 같은 밴드가 아니기 때문이다. 밴드는 입력 순서와 무관하지만 후보 집합이 바뀌면 기준점도 바뀔 수 있다. 최대 시간이 40분인 역보다 42분인 역이 차이를 이유로 먼저 나올 수도 있다. 따라서 3분 옵션에서 “최장 시간이 절대 최소”라고 설명해서는 안 되며 옵션 적용 사실을 문구에 덧붙인다. 오차는 측정 신뢰구간이 아니라 제품의 동점 정책이다.

### favor의 상한 근거와 한계

상한은 목적지마다 달라지는 “개인별 가장 가까운 역” 대신 **모두가 납득할 fair 기준역의 부담**과 비교한다. `[30,30]`이 기준이면 다른 사람의 상한은 45분이다. `[10,44]`는 허용하고 `[0,70]`은 제외한다. 20분인 사람은 최대 10분 증가, 40분인 사람은 최대 15분 증가다. 둘 중 더 엄격한 상한을 쓰므로 짧은 통근과 긴 통근 모두에 제한을 둔다.

기준역은 허용오차와 무관하게 항상 엄밀한 fair 1위로 고정한다. 기준역 자체가 상한을 만족하므로 공통 도달 후보가 있다면 favor의 후보가 전부 사라지지 않는다. 기본 0분에서는 우대 대상의 시간도 기준역보다 늘지 않는다. 우대 대상의 시간이 같은 경우 최장→차이→합계로 고른다. 허용오차 옵션에서는 우대 시간도 그 폭 내에서 늘 수 있다.

기준역에서 집까지 0분인 다른 사람에게는 증가를 허용하지 않는다. 기준역이 후보 목록에 종속되는 점, 15분/50%가 사용자 조사로 검증된 값이 아니라는 점은 알려진 한계다. “오늘은 A 쪽으로, B는 공평 추천 대비 +14분(상한 +15분)” 같은 보조 문구를 실제 UI에 권고한다.

## 추천 이유 자동 생성

주관적인 종합 점수 대신 실제 계산값과 순위 정책으로 문구를 만든다. 1위와 대안의 문구를 구별한다.

| 모드 | 1위 템플릿 | 예시 |
|---|---|---|
| fair | `{인원 표현} {M}분 안쪽, 가장 공평 · 최장 {M}분 / 차이 {D}분 / 합계 {S}분` | 둘 다 20분 안쪽, 가장 공평 · 최장 20분 / 차이 2분 / 합계 38분 |
| fast | `합계 {S}분, 합계 우선 1위 · 최장 {M}분` | 합계 34분, 합계 우선 1위 · 최장 24분 |
| favor | `{이름} 우선 {Tp}분 · 다른 사람 상한 준수 ({개인별 상한})` | A 우선 10분 · 다른 사람 상한 준수 (B 27분) |

2명이면 “둘 다”, 3~4명이면 “N명 모두”를 쓴다. fair 대안에는 “공평 모드 대안”, fast 대안에는 “빠른 만남 대안”을 쓴다. 허용오차가 양수면 `({값}분 동점 옵션)`을 붙인다. 화면은 문구와 함께 각 사람의 분·환승 수를 항상 보여준다. `reasonCode`는 문구 번역과 클라이언트 표현에 쓰고 골든 테스트는 역 ID를 정확히 검증한다. JSON의 `reason`은 각 시나리오의 기대 판단 근거다.

## 환승과 시간 행렬 생성

물리적 역 하나를 `(역 ID, 노선 ID)` 노드로 확장한다. 같은 노선의 인접역 간에는 주행시간 간선, 같은 역의 다른 노선 간에는 환승 보행시간 간선을 둔다. 다익스트라는 비용 `(분, 환승 수)`를 사전식으로 최소화한다. 따라서 시간 동률일 때만 환승이 적은 경로를 택한다. 출발역의 모든 노선 노드를 비용 0으로 시작하여 첫 승차는 환승으로 세지 않고, 도착역의 노선 노드 중 최소 비용을 택한다.

실제 서비스에서는 주행·환승 보행·대기·역 출입 시간을 무엇까지 포함했는지 행렬 버전에 고정해야 한다. 방향·급행·분기·직결운행 여부도 실제 간선에 반영해야 한다. 열차를 계속 타는 직결 노선 경계는 이름만 바뀌었다고 환승 처리하면 안 된다. 순위용 시간과 환승 수를 각각 독립적인 최적화 결과에서 가져오면 서로 다른 경로가 섞이므로 금지한다.

권고는 실제 소요시간 외에 `환승 1회=5분` 같은 인지적 벌점을 기본 적용하지 않는 것이다. 실제 환승 보행시간과 벌점을 중복 가산할 수 있고 사용자가 “왜 30분을 35분이라 부르는가”를 이해하기 어렵기 때문이다. 추후 환승 적게 선호 기능은 “소요시간 30분 / 환승 1회 / 선호 반영 별도 순위”로 구별할 수 있다.

장난감 데이터는 다음과 같다. 모두 양방향, 동일 노선 간격이 일정하며 역 X·Y·Z에서 노선 간 이동은 4분/환승 1회다. 실제 역명이나 실측 자료가 아니다. 최초 대기·열차 간격·출입 시간은 0으로 가정한다.

```text
red   R1—R2—X—R4—Y—R6—R7   (구간당 5분)
blue  B1—B2—X—B4—Z—B6—B7   (구간당 6분)
green G1—G2—Y—G4—Z—G6—G7   (구간당 6분)
```

18개 출발역마다 다익스트라를 돌려 18×18 시간·환승 행렬을 만들고, 요청에는 N×C를 추출한다. 프로토타입 예제는 R1/B7 출발, X/Y/Z/R4/B4/G4 후보이며 fair와 fast, 두 사람의 favor 결과가 달라지는 것을 출력한다. 우선순위 큐는 Python 표준 `heapq`를 사용한다. 확인한 사실: 이 모듈은 최소 원소를 꺼내는 힙 연산을 제공한다([Python 공식 문서](https://docs.python.org/3/library/heapq.html), 확인일 2026-11-12).

## 귀갓길 막차 계산 명세 — 후속 구현

**표시할 값:** “이 만남역에서 A의 집 근처역까지 갈 수 있는 마지막 열차 출발 23:40 / 역에 들어갈 권고 시각 23:35”. 단순히 해당 역 마지막 열차가 아니라 **최종 목적지까지 연결되는 여정**이어야 한다. 모임 장소에서 역 입구까지 보행은 별도이며 위치가 없으면 계산할 수 없다고 밝힌다. 출발역이 곧 집 근처역이라는 보장도 없으므로 귀가역을 별도로 받거나 “입력 출발역 기준”을 표시한다.

필요한 데이터와 요청 맥락:

- `serviceDate`, `Asia/Seoul` 시간대, 평일/주말/공휴일 운행 달력과 예외일, 데이터 버전·갱신시각.
- `tripId`, 운행일 ID, 노선/진행방향/분기·종착역, 정차 순서, 승강장별 도착·출발시각, 승하차 허용 여부. 급행의 통과역과 중간 종착도 구별.
- 역·승강장 연결, 환승 최소 보행시간, 환승 금지, 역 출입시간. 동일 열차의 직결 구간을 식별하는 정보.
- 사용자별 귀가역(선택적으로 최종 보행 및 도착 마감시간), 만남 날짜, 기본 입장 여유 5분이라는 제안값.
- 취소/운행 변경 정보를 받지 못하면 “시간표 기준”으로 명시. 정적 자료만으로 실제 운행 보장 문구를 쓰지 않는다.

확인한 사실: GTFS Schedule에는 `trips`, `stop_times`, `calendar`, `calendar_dates`, `transfers`, `pathways` 구조가 있으며 운행일의 자정 이후 시간을 24시 초과로 나타낼 수 있다([공식 명세](https://gtfs.org/documentation/schedule/reference/), 확인일 2026-11-12). 이는 필요한 데이터 형태의 참고이며 수도권 전체에 이 형식의 완전한 데이터가 제공된다는 주장은 아니다.

언어와 무관한 정확성 우선 절차:

1. 요청 운행일과 인접 운행일 중 검색 창과 겹치는 열차를 절대시각으로 정규화한다. `24:15`는 같은 운행일에서 다음 날 00:15다. 단순 문자열 시각 비교는 금지한다. 검색 창은 해당 밤의 운행 종료까지 포함하도록 데이터로 정하고 자정에 잘라버리지 않는다.
2. 각 열차의 역별 도착/출발 이벤트를 노드로 만드는 시간 확장 그래프를 구성한다. 같은 열차 이동, 다음 출발까지의 대기, 최소 환승시간을 충족하는 승강장 이동, 승하차 가능 간선을 추가한다.
3. 각 사람의 귀가역 도착 이벤트를 종점 집합으로 잡아 역방향 도달성을 구한다. 도착 마감이 있으면 그 이전의 이벤트만 종점으로 삼는다.
4. 후보 만남역의 탑승 가능 출발 이벤트 중 그 종점에 도달하는 **가장 늦은 이벤트**를 구한다. 그 경로와 각 환승 시각을 보관한다. 최종 도착 경로가 없으면 `unavailable`이고, 시간표 자체가 없으면 `unknown`으로 구별한다.
5. 출발 승강장까지 입장시간과 여유 5분을 뺀 `latestStationEntryAt`을 구한다. 여러 출발 승강장의 입장시간이 다르면 마지막 열차 시각과 별도로 **입장 가능시각이 최대인 여정**도 비교해야 한다. 두 값이 다른 경로를 뜻하면 각각의 경로를 표시한다.
6. 모두 함께 헤어질 권고 시각은 유효한 개인별 입장 가능시각의 최솟값이다. 한 명이라도 unknown이면 단체 마감시각을 확정하지 않는다. 현재시각을 지났다면 “오늘 귀가 가능 막차 지남”을 표시하고 다음 날 첫차로 대체하지 않는다.

출력 확장 예: `personId`, `destinationStationId`, `status`, `serviceDate`, `latestBoardAt`(시간대 포함 ISO 시각), `latestStationEntryAt`, `arrivalAt`, `itinerary`, `dataVersion`, `asOf`, `basis="timetable"`. 위에서 예시로 든 23:40은 실제 운행시각이 아니다. 최초 버전은 막차를 추천 카드의 별도 정보로 표시하고, 사용자 요청 없이 순위에 섞지 않는 것을 권고한다.

후속 막차 검증 필수 항목: 자정 넘는 환승, 주말/공휴일 달력 예외, 더 늦은 중간종착 열차 탈락, 마지막 환승 1분 부족, 운행 취소, 귀가역 미입력/자료 누락, 입장시간이 다른 승강장. 이번 16개 순위 골든 시나리오가 이 검증을 대체하지 않는다.

## 결정 필요

- 기본 동점은 엄밀한 0분을 유지할지, 사용자 조사 후 3분 옵션을 기본화할지. 후자는 엄밀한 minimax와 다르다.
- favor의 15분/50% 상한을 그대로 쓸지, 더 엄격하게 할지. 0분 기준자의 이동을 전혀 늘리지 않는 동작이 적합한지.
- 실제 시간 행렬에 최초 대기·역 출입을 포함하는 범위, 시간대별 행렬 필요 여부와 데이터 갱신 주기.
- 귀가역을 별도로 받을지, 출발역 기준이라는 안내로 시작할지. 막차 시간표 데이터의 확보 범위·갱신·장애 처리.
- 막차 정보를 순위와 분리해 보여줄지, 명시적인 “귀가 가능만” 필터로 확장할지. 입장 여유 5분의 제품 기본값 확정.
