# R1 작업 노트: 웹 방(각자 입력) 화면

검증일: 2026-11-15. 서버의 방 API는 그대로 쓰고(변경 없음), 웹에 방 흐름을 붙였다. 화면 캡처는 [`r1-screens/`](r1-screens/).

## 1. 흐름

```
홈 ──"방 만들어서 각자 입력하기"──▶ /r/new (방장: 이름·출발역·숨기기, 추천 기준, 약속일·예상 인원)
        └─ 방 만들기 ─▶ /r/<방 ID> (방장 화면: 링크 보내기 → 친구가 들어오면 목록·결과)
친구: 링크 /r/<방 ID> ─▶ 참여(이름·출발역·숨기기) ─▶ 목록·결과 ─▶ 수정·삭제 ─▶ "실제로 어디서 만났어요?"
```

- **방 화면 한 곳**(`/r/[roomId]`)이 친구의 첫 화면이자 방장이 돌아오는 화면이다. 이 기기의 토큰으로 "내 항목"(참여자)과 방장 기능을 구분한다.
- 참여 상태: 내 항목 있음(수정·삭제) / 참여 가능 / 잠김 / 정원(4명) 초과 / 없는 방(만료·삭제·없는 ID는 서버가 같은 404). 이미 들어온 사람은 방이 잠겨도 자기 항목을 고칠 수 있다.
- 목록의 이름은 서버 `label` 그대로, "(나)"는 내 토큰이 가리키는 줄에만. 숨긴 사람은 이름을 넣었으면 그 이름, 안 넣었으면 "참가자 N"이고(data-format §8) 출발역은 "출발역 비공개"이며 시간·환승은 보인다. 본인이 숨겼으면 본인에게만 "강남 · 나에게만 보여요".
- 결과는 서버 `/rooms/{id}/result`(토큰 있으면 본인 출발역 포함). 모드 탭은 보는 사람의 화면 설정이고 처음 값은 방의 추천 기준·배려 대상이다(방 설정을 PATCH하지는 않는다). 후보 카드는 기존 결과 화면 컴포넌트를 그대로 쓴다.
- 방장 기능: 새 참여 잠그기/풀기, 방 삭제, 참여자 내보내기(처리방침 8항이 이미 약속한 기능). 모두 한 번 더 확인한다.
- "실제로 어디서 만났어요?"(`/outcome`): 참여자에게만. 약속일을 정했으면 펼쳐서, 안 정했으면 접어서 보여 준다. 한 번 답하면 이 기기에서는 다시 묻지 않는다.
- 갱신: 방·결과를 15초마다(탭이 보일 때만)·창 포커스 때 다시 불러 친구가 들어오는 것이 보인다. 요청은 분당 약 8회로 서버 일반 한도(분당 60) 안이다.

## 2. 토큰 저장 (코디네이터 결정: tech-stack 5.5 원래 계획)

| 항목 | 결정 |
|---|---|
| 위치 | `localStorage` 키 `bby.room.<방 ID 소문자>` 하나에 JSON `{v, hostToken?, participantToken?, participantId?, keepUntil, expectedCount?, resultSeenAt?, outcomeAnswered?}` |
| deviceToken | 쓰지 않는다(`/v1/anon` 호출 없음) → **쿠키 없음, 프록시 변경 없음** |
| 만료 정리 | **기기가 먼저 지우지 않는다.** 서버는 누가 고칠 때마다 만료를 7일씩 미루므로(최대 생성 후 30일) 기기가 아는 만료 시각은 금방 낡는다(검토에서 지적: 8일째에 열면 살아 있는 방의 방장 토큰이 지워지던 버그). 지우는 때는 ① 방을 열었는데 서버가 404(방 없음)라고 할 때 ② `keepUntil`(처음 저장한 시각 + 30일 = 서버 규칙상 방의 최대 수명)이 지난 기록을 사이트를 열 때(`Providers`)·읽을 때 지울 때뿐이다 |
| 정리 규칙 | 내 항목을 지우거나 내보내진 것을 확인하면 참여자 토큰만 지운다(방장 토큰이 없으면 기록 전체). 방을 지우면 전체 삭제 |
| 상태와 저장 | 기록은 컴포넌트 상태에도 들고 저장소에는 함께 쓴다. 저장소가 막혀 있어도 방금 받은 토큰을 이번 방문 동안 쓴다(참여가 성공했는데 실패처럼 보여 다시 제출해 중복 참가자가 생기는 일을 막는다) |
| `expectedCount` | 방장이 방을 만들 때 정한 예상 인원. 서버는 정원 도달도 `locked`로 응답해 잠금 버튼으로 풀 수 없으므로, 그때 버튼 대신 이유를 보여 주는 데만 쓴다 |
| 막힌 저장소 | 읽기·쓰기 모두 try/catch. 막혀 있으면 만들기·참여 화면에 "이 기기에서 나중에 고칠 수 없다"고 미리 알린다 |
| 토큰이 가는 곳 | `Authorization: Bearer` 헤더뿐이다. URL·본문·통계·미리보기·로그에 넣지 않는다(`rooms.test.ts`가 6개 호출 모두에서 URL·본문에 토큰이 없음을 확인). 방 링크는 `/r/<방 ID>` 하나다 |
| 토큰 없는 구경꾼 | 방을 보고(숨김 적용된 목록) 결과를 보고 참여는 할 수 있다(계약대로) |
| 같은 방 대소문자 | 서버가 ID를 소문자로 저장하므로 키도 소문자로 맞춘다 |
| 기억해 둔 "나" | `banbanyeok:me`(기존)를 방 만들기·참여 때도 미리 채우고 저장한다. 숨기기 설정은 기억하지 않는다 |

**멱등 키**: 같은 내용의 재시도에는 같은 키, 내용이 바뀌거나 **참여·생성·나가기가 성공하면 새 키**(서버가 같은 키의 성공 응답을 10분간 재생하므로, 나가기·내보내짐 뒤 같은 입력으로 다시 참여하면 죽은 토큰을 받던 버그를 막는다. 내보내진 사람은 낡은 토큰을 정리하는 시점에 키를 새로 만든다). 단위(`room-screen.test.tsx`)·e2e-real이 같은 입력으로 다시 참여하는 시나리오를 확인한다.

방 안에서 낡은 토큰 처리: 기록에는 참여자 토큰이 있는데 방 응답에 `isSelf`가 없으면(내보내짐·삭제) 토큰을 정리하고 참여 가능 상태로 돌아간다. **방장 토큰으로 받은 방 응답은 `isSelf`가 없으므로 캐시에 넣지 않는다**(PATCH 응답을 캐시에 넣었다가 이 검사가 내 토큰을 지우던 버그를 e2e로 잡았다).

## 3. 콜드스타트

- 방 만들기 화면은 열리자마자(`useEffect` 첫 줄) `warmUpServer()`를 부른다. **방 화면은 부르지 않는다**: 저장소를 읽은 직후 바로 다음 렌더에서 방 조회가 나가므로 미리 깨우기가 효과가 없고, 그 방 조회가 곧 서버를 깨운다.
- 첫 로딩 중에는 제목·설명이 먼저 읽히고, 카드 안 문구가 단계적으로 바뀐다(`use-slow-hint.ts`): 즉시 "방을 불러오기 중이에요" → 2.5초 "서버를 깨우는 중이에요. 방을 불러오기까지 몇 초 걸릴 수 있어요" → 8초 "조금 오래 걸리네요…". 참여·방 만들기 제출도 같은 단계 문구.
- 재시도: 5xx·연결 실패만 최대 2회(1초·2초 뒤), 4xx는 하지 않는다. 프록시 타임아웃은 15초(P8b).
- e2e(`rooms.spec.ts` 4번째)가 방 조회를 4초 지연시켜 설명이 먼저 보이고 문구가 바뀌는 것을 확인한다.

## 4. 링크 미리보기(OG)

`/r/[roomId]`·`/r/new`는 `roomLinkMetadata()`(인자 없음): 제목 "같이 만날 역 정해요", 설명 "각자 출발역을 넣으면 …", 이미지는 사이트 기본 정적 PNG(`/opengraph-image`), `noindex`. **서버를 부르지 않고 방 ID·이름·출발역이 들어갈 길이 없다**(숨기기 보장, 요청마다 이미지를 그리지 않아 Workers 무료 CPU 한도 문제도 없다). 페이지 자체도 서버 렌더링이 얇다(서버 호출·스트리밍 없음, 형식이 틀린 ID는 서버에 묻지 않고 "없는 방" 표시). 다만 라우트가 동적(ƒ)이라 요청마다 서버 렌더링을 한다: 실제 Workers CPU는 배포 계정에서 재야 한다(P8b 3절 `/s`가 중앙값 43ms였고 이 페이지는 서버 호출이 없어 더 작을 것으로 보지만 **미측정**).

## 5. 통계 (동의한 경우에만, P7 규칙)

| 이벤트 | 시점 | 속성 |
|---|---|---|
| `room_created` | 방 만들기 성공 직후 | `hidden_used`, `participant_count_expected`(정했을 때) |
| `participant_joined` | 참여 성공 직후(방장 본인은 제외) | `hidden` |
| `outcome_answered` | 만났나 답 성공 직후 | `outcome`, `meeting_station_code`(다른 역·1위 역일 때, 장소), `days_since_result`(이 기기에서 결과를 처음 본 뒤 일수) |
| `share_clicked` | 방 링크 공유·복사 | `link_type=room` |
| `result_viewed`·`mode_switched`·`station_chosen` | 기존 이벤트를 방 결과에서도 | 기존과 같음 |

- **계약 변경**(`contracts/events.json`): `room_created`·`participant_joined`의 `source`를 `server`→`client_or_server`로(서버가 아직 통계를 보내지 않아 웹이 보낸다. 서버가 보내기 시작하면 중복을 피하려고 웹 쪽을 끈다), `participant_joined.seconds_since_room_created`를 선택 속성으로(방 조회 응답에 생성 시각이 없어 웹은 알 수 없다). `room_hash`는 서버가 응답에 주는 값을 쓰기로 했는데 응답에 없으므로 보내지 않는다.
- **방 ID는 URL 속성에서도 지운다**: `redact.ts`가 `/r/<10자>`를 `/r/[room]`으로(현재·이전·진입 주소 모두). `$current_url`에 방 링크가 들어가면 방 ID가 통계에 남기 때문이다. 단위·e2e(`e2e-analytics`, 방 API를 가로채 흉내)로 방 ID·토큰·출발역·이름이 어떤 이벤트에도 없음을 확인한다.
- 동의 전에는 요청 0건·저장소 흔적 0(`ph_*`)도 같은 e2e에서 확인한다.

```text

$ pnpm e2e                           # 기본 18개 + 통계 켠 빌드 12개 통과(방 통계 시나리오 1개 추가)
$ (compose DB → migrate → seed → 서버 → next build/start) REAL_WEB_URL=… pnpm e2e:real
  7 passed (기존 3 + rooms 4), 1 skipped(라이브 PostHog)
```

e2e-real `rooms.spec.ts`(모바일 Pixel 7, 컨텍스트 2~3개): ① 방 만들기 → 링크 복사 → 친구 참여(숨김) → 방장 화면이 새로 고침 없이 갱신 → 숨긴 출발역이 목록·결과·서버 응답 어디에도 없음(시간은 보임) → 구경꾼도 같은 숨김 → 친구가 숨기기를 풀고 수정 → 만났나 답(204)·재방문 시 다시 묻지 않음 → 친구 삭제 → 방장 방 삭제 → 링크가 "없는 방", 토큰 없음·axe 0·CSP 위반 0 ② 잠금·정원 초과·내보내기 ③ 없는 방·형식 틀린 주소(서버 호출 없음)·만료 기록 정리 ④ 콜드스타트.

**서버 속도 제한 주의**: 방 만들기·참여는 IP당 버스트 10회다(`RATE_LIMIT_CREATE_BURST`, 하루 50). 이 e2e는 새 서버 기준 7회를 쓴다. 같은 서버로 반복 실행하면 429가 나므로 서버를 다시 띄우거나 `RATE_LIMIT_CREATE_BURST`를 올린다. CI의 `e2e-real`은 매번 새 서버라 영향이 없다.

## 10. 결정 필요 / 한계

1. **방 ID가 들어간 경로의 서버 렌더링 CPU**(위 4절): 실제 Workers 계정에서 측정 필요. 무료 플랜 유지 여부 결정(P8b 결정 1)과 함께 본다.
2. ~~**서버 계약 요청 1건(작은 것)**: `Room` 응답에 `createdAt`(또는 `room_hash`)을 넣어 주면 `participant_joined.seconds_since_room_created`·`room_hash`를 웹이 채울 수 있다. 지금은 생략한다.~~ → W4에서 `Room.roomHash`·`Room.createdAt`·`RoomCreated.roomHash`를 넣고 웹이 채운다(docs/setup/w4-notes.md).
3. **`room_created`·`participant_joined`는 웹이 보낸다**(events.json의 source 변경). 서버가 통계를 붙이면 웹 쪽 전송을 끄거나 서버 쪽을 끌지 정해야 중복이 없다.
4. **가짜 서버(`web/mock`)는 방을 구현하지 않는다**(501). `mise run dev:web:mock`에서 방 화면은 "서버에 연결하지 못했어요"가 된다. 방 화면 개발은 실제 서버(`mise run dev`)를 쓴다. 방을 가짜 서버에 넣을지는 필요할 때 정한다.
5. **방 설정을 PATCH하지 않는다**: 추천 기준·배려 대상은 방 생성 때 정한 기본값이고, 이후 모드 탭은 보는 사람의 화면 설정이다(방장이 모두의 기본값을 바꾸는 기능은 없다). 방 생성 때 배려 대상은 계약상 방장뿐이다("내 쪽으로").
6. **"내 방 목록"은 없다**(deviceToken 미사용 결정). 링크를 잃으면 브라우저 방문 기록으로 돌아와야 한다. 기기·브라우저를 바꾸면 내 항목은 고칠 수 없다(방장이 내보내고 다시 참여하는 우회, 처리방침 8항의 이메일 요청).
7. **정원 안내 문구**: 서버는 `expectedCount`가 차면 `locked`로 응답해 "방장이 잠갔다"와 "인원이 찼다"를 구별할 수 없다. 두 경우를 한 문구로 안내한다.
8. 결과가 길면(후보·방장 설정·만났나까지) 화면이 길어진다. 3인 이상 실제 사용 후 접기 등을 다듬을 수 있다.
