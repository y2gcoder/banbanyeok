## 1. 계산

설계안 그대로다. 달라진 것과 구현하며 찾은 것만 적는다.

**열차 다시 잇기.** 번호 없는 노선(TAGO)은 역별 시간표의 줄을 "같은 종착역, 다음 역 예상 시각 ±90초"로 잇는다. 이웃은 **종착역 쪽**만 본다(노선 묶음의 역 그래프에서 종착역에 더 가까운 이웃. 여행 그래프의 주행 간선에서 얻는다). 종착역을 그래프에 놓지 못하면 잇지 않는다. 같은 (역, 종착역)의 줄이 가장 많이 맞는 이웃 하나만 쓴다. 서울 1~8호선(S5)은 열차 번호로 묶는다. 서울 구간으로 이어 달리는 열차는 경계역에서 같은 묶음·같은 종착역·출발 45초 안이면 한 열차로 합친다.

**도착 시각이 없는 줄은 정차가 아니다(구현하며 찾음).** 설계안은 "급행은 통과역에 줄이 없다"고 가정했는데 틀렸다. TAGO는 급행이 지나가기만 하는 역에도 줄을 싣고, 그 줄은 도착 시각이 비어 있다(9호선 증미: 평일 19시 이후 145줄 중 68줄). 이 줄을 정차로 읽으면 급행이 서지 않는 역에서 타고 내리는 없는 직행이 생긴다. 발행 게이트(물리 상한)가 평일 29칸·휴일 30칸을 잡았고, 규칙을 고친 뒤 0이다.
- 내릴 수 있는 곳: 도착 시각이 있는 줄.
- 탈 수 있는 곳: 도착 시각이 있는 줄, 또는 열차가 운행을 시작하는 줄(이은 열차의 첫 줄이고, 앞 역에 같은 종착역 열차가 예상 시각 ±5분 안에 없을 때). 앞 역에 그런 열차가 있으면 끊긴 급행일 수 있으므로 타지 못하는 줄로 본다(이른 쪽).
- 운영사별로 보면 도착 시각이 전혀 없는 역은 노선의 양 끝(시발역)뿐이고, 섞여 있는 역은 급행 통과(9호선, 공항철도 직통, 경의중앙·경춘·수인분당·1호선·4호선 안산선)이거나 차량기지 출발이다.

**역방향 탐색.** 상태는 (역, 노선 묶음)이다. 갈아탈 때마다 `max(10분, 걷는 시간 × 2 + 5분)`을 둔다. 걷는 시간은 여행 그래프의 환승 간선에서 묶음 쌍별로 가져오고(방향별), 쌍이 없으면 그 역에서 가장 긴 값, 그것도 없으면 0이다. 같은 묶음 안에서 열차를 바꾸는 것도 10분이다. 20:00~27:00에 타는 열차만 본다.

**분류.** 표에는 시간표에서 읽은 분이 그대로 들어간다(10분 단위 내림은 화면 몫).
- 직행 확정: 열차 한 대, 그 노선·요일 종류가 공식표 대조를 통과(`last-train.json`의 `exact`).
- 여유 시각: 갈아타는 길, 또는 대조 전 노선의 직행. 갈아타는 길은 10분 단위로 내린 값이 직행의 보이는 값보다 늦을 때만 고른다.
- 확인 필요: 길을 못 찾음.

**토요일(운영자 결정).** `data/config/last-train.json`의 `days`가 요일 종류별 노선 허용 목록이다. 토요일은 서울교통공사 1~8호선만 있다. 목록에 없는 노선의 줄은 아예 읽지 않으므로, 나온 길은 모두 허용된 노선으로만 이어진다. TAGO 토요일 시간표를 받게 되면 `tagoGroups`에 묶음을 더하고 `build`를 다시 돌리면 켜진다. 다른 요일 시간표로 대신하지 않는다(T2의 주말 대체는 배차 계산에만 쓰고 막차에는 쓰지 않는다. `TagoInput.raw`).

**칸 분포**(82,931칸 = 653 × 127, 대각 127칸 포함).

| 요일 종류 | 열차 | 직행 확정 | 여유(직행) | 여유(환승) | 확인 필요 |

## 2. 발행 게이트와 회귀 검사

`build`는 아래를 모두 통과해야 산출물을 쓴다(`data/config/last-train-report.json`에 결과). `validate`는 다시 계산해 발행된 표와 대조한다.

| 검사 | 평일 | 토요일 | 휴일 |
|---|---|---|---|
| 번호 가린 채점(서울 1·3~8호선): 쌍 / 일치 / **늦음** / **없는 직행** / 이름 / 빠짐 | 8,169 / 7,993 / **0** / **0** / 103 / 73 | 8,168 / 8,096 / **0** / **0** / 0 / 72 | 8,168 / 8,096 / **0** / **0** / 0 / 72 |
| 여유를 늘려(15분, 3배 + 10분) 다시 계산했을 때 늦어진 칸 | 0 | 0 | 0 |
| 직행이 전체 최선보다 늦거나, 분류와 값이 어긋난 칸 | 0 | 0 | 0 |
| 물리 상한(보인 시각 + 주행시간의 60% − 5분 > 집 역 마지막 도착)을 넘는 칸 | 0 | 0 | 0 |
| 공식표 표본 | 26건 모두 일치 (3절) | — | (평일과 합쳐 26건) |

- **번호 가린 채점**: 열차 번호가 있는 서울 노선에서 번호를 가리고 번호 없는 노선과 똑같이 다시 이은 뒤, 역 쌍마다 마지막 직행 출발을 정답과 견준다. 2호선은 뺀다(순환선은 두 방향이 종착 이름을 같이 써서 이 방법으로 잇지 않는다. 번호 없는 노선에 순환선은 없다). 역간 시간은 정답 열차의 중앙값을 썼다. 빠짐 72~73쌍은 6호선 응암 순환 구간(한 방향 운행이라 "종착역 쪽 이웃" 판정이 반대로 난다)이고 이른 쪽이다.
- **물리 상한**은 거친 검사다. 급행은 그래프(완행 기준) 주행시간의 약 68%로 달리므로 비율을 60%로 잡았다. 방향이 틀리거나 노선을 넘나드는 없는 열차는 걸리지만, 급행 통과 같은 미세한 문제는 정차 규칙이 막는다.
- **독립 오라클**: `prototype/last_train.py`가 같은 규칙을 Python으로 따로 구현한다. 고정 입력(축·노선 그래프·역간 시간·걷는 시간·허용 노선)은 파이프라인이 쓴 `build/last-train/problem.json`에서 받고 시간표 줄과 역 이름 대응은 캐시에서 직접 읽는다. 세 요일 종류 248,793칸(시각이 있는 185,129칸 포함)에서 **다른 칸 0**(42 s).
- **CI에서 도는 것**: 원자료가 저장소에 없으므로 위 검사는 로컬 `build`·`validate`에서 돈다. CI는 장난감 노선도(`pipeline/src/test/resources/last-train/toy.json`: 급행 통과 줄, 단축 운행, 중간 출발, 끊긴 통과 줄, 직통 경계, 방향별 걷는 시간)로 Kotlin 결과와 오라클의 기대 칸(`toy.expected.json`)을 대조하고, 오라클 테스트(`prototype/test_last_train.py`)가 기대 파일을 다시 만들어 본다.

## 3. 운영사 공식 시간표 대조 (2026-11-20)

운영사 역별 시간표 페이지를 2026-11-20에 읽어 `data/config/last-train-official.csv`에 적었다(만날 역, 집 역, 요일 종류, 막차 시각, 행선지, 주소, 확인일). 열차 한 대로 가는 쌍의 마지막 출발과 그 열차의 행선지를 본다. 26건 모두 분과 행선지가 같다.

| 노선 | 표본 | 결과 | 출처 |
|---|---|---|---|
| 신분당선 | 신사·논현·신논현·강남·양재·판교에서 광교·정자·신사까지 12쌍 × 평일·휴일 = 24건. 광교행, 정자까지만 가는 열차, 신사 방면, 자정 넘김(24:00~24:42) 포함 | 24건 일치 | `https://www.shinbundang.co.kr/dxline/dxline_time_gy.jsp?sb_cd=SB001`~`SB005`, `SB008` |
| 공항철도 | 서울역 → 검암, 평일·휴일 2건 (24:00) | 2건 일치 | `https://www.airportrailroad.com/train/normal/info/010/0` |

- 가능성 확인 보고서의 신분당 10건(평일·휴일 5쌍)은 모두 이 24건 안에 있고 값이 같다.
- **직행 확정으로 켠 것은 신분당선(평일·휴일)뿐이다.** 공항철도는 표본이 한 쌍이고 운영사 표가 행선지(인천공항2터미널행·검암행)를 한 표에 섞어 보여 더 넓히지 못했다. 표본은 게이트에 넣었지만 `exact`에는 넣지 않았다.
- 운영사 표는 "평일 / 주말 및 공휴일" 두 가지다(신분당선). 토요일은 TAGO 시간표가 없어 계산하지 않으므로 대조할 값이 없다.
- 표본은 **한 노선으로만 직행이 되는 쌍**이어야 한다. 양재→신사는 3호선 직행이 더 늦어(24:46) 신분당선 표와 다르게 나오므로 표본에서 뺐다.
- 서울교통공사(1~8호선), 9호선, 코레일 계열, 인천·경전철은 대조하지 못했다. 역 시간표 페이지가 스크립트로 그려져 읽지 못했거나 시간이 모자랐다. 이 노선들의 직행은 여유 시각으로 나간다. 노선을 대조해 `exact`에 더하고 다시 발행하면 분 단위로 바뀐다(게이트가 그 노선·요일 종류의 통과 표본이 CSV에 있는지 확인한다).

## 4. 서버와 계약

- **읽기.** `ArtifactLoader`가 세대 3 → 2 → 1 순서로 `manifest.json`과 dataVersion이 같은 첫 세대를 고른다. 막차 표는 구분 행렬처럼 기동 뒤 뒤에서 읽고 검사한다. 세대 1·2 데이터, 읽는 중, 검증 실패면 응답에서 `lastTrainBasis`와 `lastTrains`만 빠진다(실패는 한 번만 기록). 요청은 계산 전에 최대 2초 기다린다.
- **붙이기.** `RecommendationService`가 순위(상위 3)를 정한 **뒤** 카드마다 사람별 칸을 읽어 붙인다. 순위·시간·이유는 그대로다(막차 표가 있는 서버와 없는 서버의 응답이 막차 키만 빼면 글자까지 같음을 테스트한다). 요청한 구분으로 계산하지 못해 평일 낮으로 대신 계산한 응답에는 붙이지 않는다.
- **숨김.** 출발역을 숨긴 참가자의 항목은 `RecommendRequest.viewerId`가 그 참가자일 때만 들어간다. 방 결과는 토큰으로 확인한 본인(`isSelf`)을 넘기고, 미리보기는 토큰 없이 읽으므로 늘 빠진다. `/recommend`에는 숨김이 없다. 숨긴 사람의 출발역만 다른 두 방에서 다른 사람이 받는 막차 JSON이 같음을 테스트한다. 로그에는 지금처럼 요청 조건을 남기지 않는다.
- **시각을 내지 않는 경우**(`lastTrainBasis.unavailable`, 모든 항목이 `check`): 요일 종류를 고르지 않음(`day_unknown`: `/recommend`에 `timeSlot` 없음, 방에 약속일 없음), 약속일이 공휴일 목록 밖(`date_out_of_range`), 수집일에서 120일 지남(`stale`, 서울 날짜 기준).
- **v=1 링크.** 서버는 링크 버전을 모른다. 웹이 `v=1` 링크에서 `timeSlot`을 빼고 요청하면 순위는 지금과 같고(평일 낮) 막차는 `day_unknown`으로 온다. 화면에서 숨기는 것은 다음 PR이다.
- **계약.** `Result.lastTrainBasis`, `Candidate.lastTrains[]`, `PreviewTime.lastTrain`, `RoomPreviewResult/Decided.lastTrainBasis`. 모두 선택 필드라 옛 웹은 무시한다. `kind`는 `direct`(분 그대로) / `margin`(10분 단위로 내려 보임, `transfer`로 갈아타는 길인지 구분) / `check`(시각 없음).

**서버 기동**(로컬 맥, AppCDS 없음, 8회씩 번갈아 측정, 기동 시각 기준 ms).

| 데이터 | 기본 행렬 검사 | 구분 행렬 검사 | 막차 표 검사 | Ktor 준비 p50 (최소~최대) |
|---|---:|---:|---:|---|
| 세대 2(막차 표 없음) | 137.5 | 167.5 | — | 286.0 (281~292) |
| 세대 3(막차 표 있음) | 137.0 | 164.5 | 163.5 | 286.5 (281~293) |

막차 표 검사는 Ktor가 준비되기 약 120 ms 전에 끝난다. Cloud Run 실측은 배포 뒤 `scripts/measure-coldstart-revisions.sh`로 한다(미측정).

## 5. 실행

```sh
./gradlew :pipeline:run --args=build       # 캐시 필요(S1/S3/S4, TAGO, 서울 S5). 막차 게이트 실패 시 산출물을 쓰지 않는다
./gradlew :pipeline:run --args=validate    # 막차 표를 다시 계산해 발행된 것과 대조
python3 -B prototype/last_train.py compare build/last-train/problem.json data/raw data/artifacts/dev/lt.bin   # 독립 오라클(약 40초)
python3 -B prototype/last_train.py expect pipeline/src/test/resources/last-train/toy.json                     # 장난감 기대 칸
```

`build`는 이제 서울 S5 캐시(`data/raw/seoul`)도 읽는다(전에는 배차 재계산 때만 읽었다).

## 6. 배포

`deploy-server`가 산출물을 발행한 뒤 새 리비전을 올린다. 발행은 해시 파일 → `manifest.v3.json` → `manifest.v2.json` → `manifest.json` 순서다(`scripts/publish-artifacts.sh`). 운영 중인 옛 리비전은 `manifest.v2.json`을 계속 읽으므로 발행 뒤에도 기동한다(되돌리기 포함). 옛 스크립트로 되돌려 v3가 남아도 새 서버는 dataVersion이 다른 v3를 쓰지 않는다. 웹은 이번 PR에서 바뀌는 것이 없다(생성 타입과 역 색인의 데이터 버전만).
