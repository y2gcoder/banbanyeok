|---|---|---|---|
| 역 레지스트리 | `data/registry/stations.json` | JSON, append-only | 사람 + P2 (git) |
| 후보 목록 | `data/registry/candidates.json` | JSON | 사람 + P2 (git) |

**manifest 세대**(`manifest.schemaVersion`)에 맞는 구성 파일 형식을 읽는다. 세대 2는 구분별 od 행렬(§9), 세대 3은 막차
표(§10), 세대 4는 사람별 경로 그래프(§11)를 더한다. 세대 1~4의 구성 파일은 모두 1판이다.
별도 포인터가 있는 권역 세대 5는 레지스트리 JSON과 rg.bin만 2판을 쓴다(§12).

## 2. 역 코드

- **3자, ASCII, 소문자·숫자 base32.** 알파벳(32자, Crockford에서 `i l o u` 제외):
  `0123456789abcdefghjkmnpqrstvwxyz`
- 코드 값(`codeValue`): 각 글자를 알파벳 위치(0..31)로 읽어 5비트씩 이어 붙인 15비트 정수.
  `value = c0·1024 + c1·32 + c2`, 범위 `0..32767`(= 32³ − 1).
  예: `"03v"` → 0·1024 + 3·32 + 27 = 123.
- **코드의 문자열 사전순(ASCII) = 코드 값 오름차순.** 알파벳이 ASCII 코드 순으로 정렬돼 있어 항상 성립한다(`0..9` < `a..z`).
  그래서 JVM·TypeScript·Python의 정렬 차이가 생기지 않는다.
- reader는 **소문자 정규형만** 받는다. `O→0` 같은 혼동 문자 치환이나 대문자 허용은 링크 계층(P6)의 선택이며, 레지스트리와 od.bin은 정규형만 가진다. 허용하지 않는 코드는 오류다.
- **안정 ID = 코드.** 한 번 발급된 코드는 같은 물리 역을 영구히 가리킨다. 재사용하지 않고 삭제하지 않는다(§3).
  발급 방법(P2): 암호학적 난수로 미사용 코드를 뽑아 `stations.json`에 기록한다. 역 이름·좌표에서 계산하지 않는다(개명·이전에 영향받지 않게).
  인접 코드가 비슷한 역이 되지 않도록 순차 발급은 쓰지 않는다.
- 단위는 **환승역을 묶은 물리 역**이다(`docs/research/algorithm.md`의 공통 역 ID). 기관별 코드는 `sources`에만 둔다.

## 3. 레지스트리 `stations.json`

```json
{
  "schemaVersion": 1,
  "registryVersion": 1,
  "stations": [
    {
      "code": "03v",
      "name": "B1",
      "status": "active",
      "lat": 37.5,
      "lng": 127.0,
      "lines": ["blue"],
      "aliases": [],
      "sources": {"fixture": "B1"},
      "addedIn": 1
    }
  ]
}
```

| 필드 | 형 | 규칙 |
|---|---|---|
| `schemaVersion` | 정수 | 반드시 reader가 지원하는 값 |
| `registryVersion` | 정수 ≥ 1 | 내용이 바뀔 때마다 1씩 증가. od.bin 헤더·manifest가 같은 값을 가진다 |
| `stations[].code` | 문자열 | §2 정규형. 파일 안에서 유일. **`stations`는 `code` 오름차순**이어야 한다 |
| `name` | 문자열 | 비어 있으면 안 된다. 현재 표시 이름 |
| `status` | `"active"` \| `"deprecated"` | 폐역·통합은 삭제하지 않고 `deprecated` |
| `lat`, `lng` | 수 | 십진 도(WGS84). 소수 6자리까지 쓴다 |
| `lines` | 문자열 배열 | 지나는 노선 표시명. 순서는 임의지만 결정적(정렬)으로 쓴다 |
| `aliases` | 문자열 배열 | 옛 이름·별칭. 검색에 쓴다 |
| `sources` | 문자열→문자열 객체 | 기관별 코드(`kric:<기관>:<노선>`, `seoul:…`, `tago:<TAGO 노선명>`, S1에 없는 역의 좌표 출처 `wikidata`, …). 값은 불투명 문자열 |
| `addedIn` | 정수 | 처음 들어간 `registryVersion` |
| `deprecatedIn` | 정수, 선택 | `status=deprecated`일 때만 |
| `replacedBy` | 코드, 선택 | 이 역을 대체하는 코드. 레지스트리에 존재해야 한다. 소비자(서버·웹 역 인덱스)는 사슬을 따라 `active` 코드까지 가서 그 코드로 계산·표시한다(순환·끊긴 사슬은 파이프라인 게이트가 거부한다) |
| `region` | `"capital"` \| `"busan"` | 레지스트리 2판의 각 역에서 필수. `replacedBy`는 같은 권역이어야 한다. 1판 작성 시 생략한다 |

**append-only 규칙** (옛 링크 보존, `RegistryCompatibility`와 CI가 검사):
이전 `main`의 레지스트리에 있던 코드는 새 레지스트리에도 있어야 한다. 코드는 같은 `addedIn`을 유지하고, `status`는 `active → deprecated`로만 바뀐다(되돌림 금지). `registryVersion`은 줄어들지 않는다.
내용이 바뀌었는데 `registryVersion`이 그대로면 위반이다(파이프라인이 증가시킨다).

### 후보 목록 `candidates.json`

```json
{"schemaVersion": 1, "registryVersion": 1, "candidates": ["0aj", "…"]}
```

추천 가능한 만남 후보역. 코드 오름차순, 중복 없음, 모두 레지스트리에 `active`로 있어야 한다(`CandidateList.validateAgainst`). od.bin의 후보 축(§4)과 **같은 집합·같은 순서**여야 한다.

## 4. `od.bin` — 출발역 N × 후보 M 행렬

- **리틀 엔디언.** 모든 다바이트 정수는 하위 바이트가 먼저. 부호 없음(u8/u16/u32/u64).
- 시간은 **정수 초**. 환승은 정수 횟수. 두 값은 같은 최단 경로의 것이다(시간 동률일 때 최소 환승, `algorithm.md`).
- 경로 도달 불가: 시간 `0xFFFF`와 환승 `0xFF`를 **같은 칸에 함께** 쓴다. 한쪽만이면 오류.
- 대각(출발역 = 후보역)은 시간 0, 환승 0이어야 한다(파이프라인 검증 게이트의 불변식. reader는 강제하지 않음).

### 4.1 헤더 (고정 32바이트)

| 오프셋 | 크기 | 필드 | 값 / 규칙 |
|---|---|---|---|
| 0 | 4 | `magic` | ASCII `BBOD` |
| 4 | 2 | `formatVersion` | u16, 지금 `1`(구성 형식 판, §1) |
| 6 | 2 | `headerSize` | u16, 지금 `32`. 이후 버전에서 헤더가 커지면 reader가 건너뛴다 |
| 8 | 4 | `flags` | u32, 지금 `0`. 0이 아니면 거부 |
| 12 | 4 | `registryVersion` | u32. 이 행렬이 만들어진 레지스트리 버전 |
| 16 | 4 | `originCount` N | u32 |
| 20 | 4 | `candidateCount` M | u32 |
| 24 | 8 | `reserved` | u64, `0`이어야 한다 |

### 4.2 본문 (헤더 바로 뒤, 패딩 없음, 이 순서)

| 구간 | 크기 | 내용 |
|---|---|---|
| 출발역 코드 | 2·N | u16 `codeValue`, **엄격한 오름차순**(중복 없음), 값 < 32768 |
| 후보역 코드 | 2·M | 같은 규칙 |
| 시간 | 2·N·M | u16 초, 행 우선(row = 출발역 인덱스, col = 후보 인덱스). `0xFFFF` = 도달 불가 |
| 환승 | N·M | u8, 같은 배치. `0xFF` = 도달 불가 |

총 길이는 정확히 `headerSize + 2N + 2M + 2NM + NM`바이트다. 짧거나 길면 거부한다(잘림·이어붙임 방지).
시간의 최댓값은 `65534`초(약 18시간 11분)다. writer는 이를 넘으면 거부한다. 더 크게 필요하면 `formatVersion`을 올려 u32로 바꾼다.
환승의 최댓값은 `254`다.

코드 축은 od.bin 자체가 가지므로 **레지스트리의 순서와 무관하게 읽을 수 있고**, 출발역은 이진 탐색으로 인덱스를 찾는다. 후보 인덱스도 같다.

### 4.3 결정성과 해시 규칙

- 같은 입력이면 **바이트가 같아야 한다**(코드 정렬, 고정 헤더, 시간 기록·무작위 없음). 생성 시각은 manifest에만 둔다.
- 해시: **SHA-256**, 파일 전체 바이트에 대해, 소문자 16진수 64자. 정규화(줄바꿈·공백 변환)는 하지 않는다.
- 발행 파일 이름은 `<종류>.<해시 앞 16자>.<확장자>`(예: `od.19cc73e7f8df1451.bin`). 내용이 같으면 이름이 같고, 이름이 같으면 내용이 같으므로 `Cache-Control: immutable`로 내보낼 수 있다.

## 5. `manifest.json`

```json
{
  "schemaVersion": 1,
  "minClientSchema": 1,
  "dataVersion": "20261112.1",
  "generatedAt": "2026-11-12T00:00:00Z",
  "registryVersion": 1,
  "timeModel": "fixture-v1",
  "originCount": 18,
  "candidateCount": 6,
  "files": {
    "registry":   {"path": "versions/20261112.1/stations.9bf91ec4c8a5cb93.json", "sha256": "…64자…", "bytes": 4674},
    "candidates": {"path": "versions/20261112.1/candidates.27d2a047085a8741.json", "sha256": "…", "bytes": 137},
    "od":         {"path": "versions/20261112.1/od.19cc73e7f8df1451.bin", "sha256": "…", "bytes": 404}
  }
}
```

| 필드 | 규칙 |
|---|---|
| `schemaVersion` | manifest 세대(§1). 기존 포인터는 `1`~`4`, 권역 포인터는 `5`(§12) |
| `minClientSchema` | 이 데이터를 읽을 수 있는 클라이언트의 **최소 지원 세대**. 클라이언트가 지원하는 최댓값 < `minClientSchema`이면 데이터를 쓰지 말고 업데이트를 안내한다. `≤ schemaVersion`. 파이프라인은 세대마다 그 세대의 수를 쓴다(세대 2에 `2`, 세대 3에 `3`, 세대 4에 `4`) |
| `dataVersion` | `YYYYMMDD.N`(N ≥ 1, 같은 날 N번째 발행). 정규식 `^[0-9]{8}\.[0-9]{1,3}$`. 방(room)이 이 값을 기록해 두 계산이 어긋나지 않게 한다 |
| `previousDataVersion` | 선택. 직전 정상 버전(롤백 안내용). 첫 발행이면 키를 생략한다 |
| `generatedAt` | UTC ISO-8601, `Z`로 끝남 |
| `registryVersion` | 위 레지스트리·후보·od.bin 헤더의 값과 모두 같아야 한다 |
| `timeModel` | 시간 행렬에 포함한 것의 식별자(예: 주행+환승 보행+평균 대기). 모델이 바뀌면 값이 바뀐다. 내용은 `data/` 문서에 둔다 |
| `originCount`, `candidateCount` | od.bin의 N, M과 같아야 한다 |
| `files.registry`, `files.candidates`, `files.od` | 필수. `path`는 manifest 기준 상대 경로(`..`·절대 경로 금지), `sha256`은 §4.3, `bytes`는 정확한 크기. `files.od`는 **기본 구분(평일 낮, `weekday-day`)** 의 행렬이다 |
| `files.seoPages` | 선택. 같은 모양 |
| `files.routeGraph` | 세대 4에서 필수, 세대 1~3에는 없어야 한다. 노선 그래프 rg.bin(§11). `files.od`와 같은 모양 |
| `files.lastTrain` | 세대 3·4에서 필수, 세대 1·2에는 없어야 한다. 막차 표 lt.bin(§10). `files.od`와 같은 모양 |
| `lastTrainAsOf` | 세대 3에서 필수, 세대 1·2에는 없어야 한다. 막차 계산에 쓴 시간표 가운데 **가장 오래된 수집일**(`YYYY-MM-DD`, 서울 날짜). 수집 영수증(`source-manifest.json`의 S5·S6 `fetched_at`)에서 오므로 같은 입력이면 같은 값이다. 서버는 이 날짜에서 120일이 지나면 막차 시각을 내지 않는다. **달력에 있는 날짜**여야 한다(`2026-02-30`은 거부: reader는 날짜 모양만이 아니라 실제 날짜인지 본다). 거부된 세대 3은 읽지 못한 세대로 보아 서버는 세대 2로 기동한다(막차만 꺼진다) |
| `lastTrainModel` | 세대 3에서 필수, 세대 1·2에는 없어야 한다. 막차 계산 규칙의 식별자(지금 `numbered-v1+walk2x5m+source3m`: 열차 번호가 있는 원천과 칸마다 대조한 직행 칸만으로 낸 표. 열차 번호 없는 줄을 다시 이은 열차도 쓰는 표는 `chain-v3+…`). 규칙이 바뀌면 값이 바뀐다 |
| `lastTrainPartialDays` | 세대 3에서 선택, 세대 1·2에는 없어야 한다. **시간표가 있는 노선만 계산한 요일 종류**의 id 목록(`weekday`·`saturday`·`holiday`, 겹치지 않게). 지금 `["saturday"]`(서울교통공사 1~8호선만). `last-train.json`의 요일별 허용 목록이 다른 요일 종류에 있는 노선을 빼면 그 요일 종류가 여기 들어간다. 서버는 이 값으로 응답의 `lastTrainBasis.partial`을 낸다. 없으면 모든 요일 종류가 전 노선이다 |
| `files.odSlots` | 세대 2·3에서 필수, 세대 1에는 없어야 한다. 키는 구분 id(§9)이고 기본 구분을 **뺀** 11개가 빠짐없이 있어야 한다. 값은 `files.od`와 같은 모양. 모든 구분 행렬은 `files.od`와 **같은 출발역·후보 축**이고 같은 `registryVersion`이다. 내용이 같은 구분(예: 토요일과 일요일·공휴일)은 한 파일을 함께 가리킬 수 있다 — 같은 `path`를 가리키는 항목은 `sha256`·`bytes`도 같아야 한다 |

**검증 순서** (서버가 새 버전을 받을 때, 실패하면 직전 정상 버전 유지):
① manifest 파싱·필드 검사 → ② `schemaVersion`/`minClientSchema` 지원 확인 → ③ 각 파일의 `bytes`와 `sha256` 대조 → ④ od.bin 헤더·길이·코드 오름차순 → ⑤ N, M, `registryVersion` 상호 일치 → ⑥ 후보 목록 ≡ od.bin 후보 축, 모든 od.bin 코드가 레지스트리에 존재 → ⑦ 구분 행렬마다 ③④와 `files.od`와 같은 축·`registryVersion` → ⑧ (서버만) 골든 샘플 → ⑨ 막차 표의 `bytes`·`sha256`, 헤더·길이·칸 불변식(§10), `registryVersion`, **축 ≡ od.bin의 축** → ⑩ 노선 그래프의 `bytes`·`sha256`,
헤더·길이·불변식(§11), `registryVersion`, 모든 노드의 역이 레지스트리에 있고 **od.bin의 모든 출발역·후보역에 노드가 있다**.
서버는 ①~⑥을 마치면 기동하고 ⑦, ⑨, ⑩은 뒤에서 한다(콜드스타트). ⑦이 끝나기 전에 온 구분 요청은 잠깐 기다리고, ⑦이 실패하면 그 서버는
기본 구분으로만 계산한다(응답의 `timeBasis`가 평일 낮이 되어 사용자에게 드러난다). **⑨가 실패해도 서버는 뜨고 순위·시간은 그대로다.**
응답에서 막차 항목(`lastTrainBasis`, `lastTrains`)만 빠진다. ⑨가 끝나기 전에 온 요청은 **기다리지 않고** 막차 없이 답한다(막차는 덧붙는
정보라 추천 응답 시간에 영향을 주지 않는다). **⑩도 같다**: 실패하거나 끝나기 전이면 응답에서 사람별 경로(`candidates[].routes`)만 빠지고
화면은 중립색 막대로 그린다.
manifest 자체는 **발행의 마지막 단계에 한 번에 교체**한다(10.3).

**세대별 객체 이름.** 발행은 manifest를 네 개 쓴다. `manifest.v4.json`은 세대 4(노선 그래프 포함), `manifest.v3.json`은 같은 dataVersion·같은
파일의 세대 3(노선 그래프 없음), `manifest.v2.json`은 세대 2(막차 항목도 없음), `manifest.json`은 세대 1(`files.odSlots`도 없음, `timeModel` = `weekday-offpeak-half-headway`)이다. reader는 모르는
키를 거부하므로 아래 세대 파일에는 위 세대의 키가 하나도 없어야 한다. 그래서 새 세대를 모르는 옛 서버(배포 틈의 옛 리비전, 되돌리기)도 자기가
아는 이름을 읽어 계속 기동한다. 순서는 해시 파일 → `manifest.v4.json` → `manifest.v3.json` → `manifest.v2.json` → `manifest.json`(마지막). reader는 자기가 아는 가장
높은 세대부터 보아 **`manifest.json`과 dataVersion이 같은** 첫 세대를 쓰고, 없으면 세대 1을 쓴다(옛 스크립트로 되돌려 `manifest.json`만 바뀐
경우 지난 높은 세대를 쓰지 않게). 어떤 세대가 없는 데이터를 발행할 때는 버킷에 남은 그 세대의 파일을 지운다. dev 산출물
(`data/artifacts/dev/`)도 같은 네 파일을 둔다.

## 6. 호환 규칙

- 필드 **추가**(JSON): `schemaVersion`을 올리지 않고 reader가 모르는 필드를 무시하는 것은 허용하지 않는다. 우리는 reader를 엄격하게 둔다(알 수 없는 키 = 오류). 새 필드가 필요하면 `schemaVersion`을 올린다.
- 형식 변경은 `schemaVersion` 증가 + `minClientSchema` 조정으로 구세대 클라이언트를 안전하게 막는다.
- od.bin의 헤더 확장은 `headerSize`로, 본문 형식 변경은 `formatVersion`으로 알린다.
- 이 폴더의 샘플(`contracts/fixtures/`)은 장난감 노선도(역 18개, 후보 6개)로 만든 것이며 실제 역·시간이 아니다.

## 7. 공유 URL 링크 코덱 (`/s`)

혼자 입력해 URL로 공유하는 흐름(서버 저장 없음)의 상태 표현이다. 웹(TypeScript), `shared/links`(Kotlin), 앱이 **각자 구현**하므로 아래 규칙과 테스트 벡터 [`golden/link-vectors.json`](golden/link-vectors.json)이 일치의 기준이다. 기준 구현은 `prototype/gen_link_vectors.py`(벡터 생성기), 새 구현은 벡터 파일의 `encode`/`decode` 항목을 모두 통과해야 한다.

형태: `/s?v=2&o=03v.130&m=f&t=weekday-day&n=<별칭>`. 정규형 쿼리는 `A-Za-z0-9-_.=&` 문자만 쓰므로 퍼센트 인코딩이 필요 없다(RFC 3986 쿼리의 unreserved 문자 + `=`, `&`). 방 링크 `/r/{roomId}`는 이 코덱의 대상이 아니다(토큰·개인 식별자는 어떤 URL에도 넣지 않는다).

| 파라미터 | 규칙 |
|---|---|
| `v` | URL 스키마 버전(데이터 버전이 아님). 지금 `2`. 구분이 생기기 전의 옛 링크 `1`도 읽는다(아래). 그 밖의 값은 `UNSUPPORTED_VERSION` |
| `o` | 출발역 코드(§2 정규형)를 `.`으로 연결, 입력 순서 = A, B, C, D. **2~4개**(`BAD_ORIGIN_COUNT`), 모든 코드가 유효(`BAD_STATION_CODE`). 같은 코드가 반복돼도 된다 |
| `m` | `f` 공평, `q` 빨리, `p<i>` 배려(`i`는 `o` 안의 0부터 시작하는 위치, 한 자리). 그 외는 `BAD_MODE`, 범위 밖은 `FAVOR_INDEX_OUT_OF_RANGE` |
| `t` | `v=2`에서 필수(없으면 `MISSING_PARAM`). 구분 id(§9, 예 `saturday-night`). 대소문자 구분, 목록에 없으면 `BAD_TIME_SLOT`. `v=1` 링크에는 `t`가 없고, 있어도 알 수 없는 키처럼 무시하며 **평일 낮(`weekday-day`)** 으로 읽는다 — 옛 공유 링크는 계속 같은 결과(평일 낮)다 |
| `n` | 선택. 별칭 목록: 각 별칭을 UTF-8로 인코딩해 **base64url(패딩 `=` 없음, `-`와 `_`)** 로 쓰고 `.`으로 잇는다(`.`은 base64url 알파벳에 없고 `o`와 같은 구분자다. `|`는 RFC 3986 쿼리에서 그대로 쓸 수 없어 쓰지 않는다). 세그먼트 수는 `o`의 개수와 같아야 하며 별칭이 없는 사람은 빈 세그먼트. 별칭은 **유니코드 코드포인트 20자 이하**(UTF-16 길이가 아님). 별칭이 하나도 없으면 `n`을 **생략**한다(`n=.`는 비정규라 `BAD_NICKNAMES`). 정규형이 아닌 base64(패딩, 표준 알파벳, 남는 비트가 0이 아님)와 잘못된 UTF-8도 `BAD_NICKNAMES` |

**인코더(정규형)**: 언제나 `v=2`이고 `t`를 늘 쓴다(평일 낮이어도). 파라미터 순서 `v, o, m, t, n`, 소문자 코드, 퍼센트 인코딩 없이 `.`을 그대로 쓴다.
**옛 링크(`v=1`)에서 읽은 상태를 다시 주소로 적을 때는 `v=1` 그대로, `t` 없이 적는다**(순서 `v, o, m, n`). `v=1` 링크는 요일·시간대를 고른 적이 없고 평일 낮은 기본값일 뿐이다. `v=2&t=weekday-day`로 올려 적으면 그 주소를 읽는 쪽(미리보기 그림 주소, 다시 공유한 링크)에서 평일 낮을 고른 요청이 되어 귀갓길 막차 시각(§10)이 실린다. 구현은 "v=1에서 읽었다"는 표시를 상태에 들고 다닌다(웹의 `slotDefaulted`). 벡터의 `encode[]`는 새로 만든 상태의 정규형만 다룬다.
**디코더**: 순서 무관, **알 수 없는 키는 무시**(유입 추적용 `utm_*` 등), 값은 먼저 퍼센트 디코딩한 뒤 해석한다(`%2E`도 받는다. 옛 구분자 `|`는 별칭 세그먼트에서 base64url 알파벳 위반이므로 `BAD_NICKNAMES`). 잘못된 퍼센트 이스케이프나 UTF-8은 `MALFORMED_QUERY`. 필수 키(`v`,`o`,`m`) 누락은 `MISSING_PARAM`, 같은 키가 두 번이면 `DUPLICATE_PARAM`. 오류는 하나만 보고하며 검사 순서는 위 표의 `v`→`o`→`m`→`t`→`n` 순이다.
**별칭이 없는 링크가 기본**이다. 화면의 사람 이름은 §8 규칙으로 서버가 만든다(별칭이 없으면 "{출발역}에서 오는 분"). 링크의 `o`에 폐기된(`deprecated`) 코드가 있으면 서버와 웹 역 인덱스가 `replacedBy`를 따라 정식 코드로 읽으므로 옛 링크도 열린다.

벡터 예시 (전체는 JSON):

| id | 쿼리 | 의미 |
|---|---|---|
| `fair_two` | `v=2&o=03v.130&m=f&t=weekday-day` | 두 사람, 공평, 평일 낮 |
| `saturday_night` | `v=2&o=03v.130&m=f&t=saturday-night` | 토요일 밤 |
| `favor_second_of_four` | `v=2&o=03v.130.225.31a&m=p1&t=weekday-day` | 네 사람, 두 번째 사람 배려 |
| `nicknames_korean` | `v=2&o=03v.130&m=f&t=weekday-day&n=66-87IiY.7KeA7Jew` | 별칭 "민수", "지연" |
| `legacy_v1_is_weekday_day` | `v=1&o=03v.130&m=f` | 옛 링크: 평일 낮 |
| `nickname_emoji_20_code_points` | `…&n=8J-ZgvCf…` | 이모지 20개 = 20자(UTF-16으로는 40) |
| `uppercase_code_rejected` | `v=1&o=03V.130&m=f` | `BAD_STATION_CODE` |
| `favor_index_out_of_range` | `v=1&o=03v.130&m=p2` | `FAVOR_INDEX_OUT_OF_RANGE` |
| `bad_time_slot` | `v=2&o=03v.130&m=f&t=sunday-dawn` | `BAD_TIME_SLOT` |

벡터 JSON 형식(2판): `encode[]`는 `{id, input:{origins, mode, favorIndex, nicknames, timeSlot}, expectedQuery}`, `decode[]`는 `{id, query, expected:{origins, mode, favorIndex, nicknames, timeSlot}}` 또는 `{id, query, expectedError}`. `nicknames`는 `null`(별칭 없음) 또는 길이가 `origins`와 같은 배열(빈 별칭은 `null`).

## 8. 참가자 표시 이름 (`label`, `shortLabel`)

화면과 추천 이유 문장에서 사람을 부르는 이름이다. **서버가 만들어** 응답의 `participants[].label`·`labelKind`·`shortLabel`에 넣고, 웹·앱은 다시 만들지 않고 그대로 쓴다. 구현은 `shared/app-logic`의 `ParticipantLabels` 한 곳이며(파이프라인의 SEO 문장도 같은 구현을 쓴다), 벡터 [`golden/display-labels.json`](golden/display-labels.json)이 기준이다.

참가자 목록의 순서(`/recommend`는 입력 순서, 방은 참여 순서)대로 한 사람씩 정한다.

| 순서 | 조건 | `label` | `labelKind` | `shortLabel` |
|---|---|---|---|---|
| 1 | 사람이 이름(별칭)을 넣었다(앞뒤 공백을 빼고 비어 있지 않음) | 그 이름(앞뒤 공백 제거, 나머지는 그대로. 이모지 포함). 같은 이름이면 입력 순서대로 ` 1`, ` 2`, …를 붙인다 | `name` | `label`과 같다 |
| 2 | 이름이 없고 출발역 이름을 안다 | `{출발역 이름}에서 오는 분`. 이 규칙을 쓰는 사람 중 같은 출발역 이름이 둘 이상이면 입력 순서대로 ` 1`, ` 2`, …를 붙인다 | `origin` | `{출발역 이름}`(번호는 같게, 예 `강남 2`) |
| 3 | 이름이 없고 출발역 이름을 모른다 | `참가자 {목록 안 순번}`(1부터) | `ordinal` | `label`과 같다 |

- **어디에 무엇을**: `label`은 문장(추천 이유, 극단 상황 문구)에, `shortLabel`은 좁은 칸(결과 카드의 시간 행, 배려할 사람을 고르는 알약, 미리보기 그림, 미리보기 설명·공유 문구의 시간 나열)에 쓴다. 입력한 것이 출발역이라 칸 안의 "홍대입구"는 맥락상 사람으로 읽힌다(V1, docs/setup/v1-notes.md).

- **번호 세기**: 2번 규칙의 번호는 2번 규칙을 쓰는 사람끼리만 센다. 이름을 넣은 사람은 세지 않는다.
- **보는 사람과 무관**: 같은 방이면 누가 보든 같은 값이다.
- **쓰지 않는 것**: 익명 사용자 ID, 참가자 ID, 토큰 같은 내부 식별자(여러 방에 걸쳐 같은 사람을 이어 볼 수 있게 되므로). "나/너/친구1" 같은 시점 표현. 보는 사람 표시 "(나)"는 클라이언트가 자기 화면에서만 붙인다.
- 이름 번호는 앞뒤 공백 제거 후 같은 이름끼리만 센다. 출발역 번호와는 별도로 센다. 입력 화면의 "나/친구1" 같은 문구는 입력 칸 안내(placeholder)일 뿐 이름이 아니다.

벡터 JSON 형식: `vectors[]`는 `{id, people:[{name, originName}], expected:[{label, kind, shortLabel}], note?}`. `name`과 `originName`이 `null`이면 각각 이름과 출발역 이름을 모르는 경우다.

## 9. 구분: 요일 유형 × 시간대 ("언제 만나요?")

시간 행렬은 구분마다 하나다. 배차가 요일·시간대마다 달라서 탑승·환승 대기(배차/2)가 바뀌기 때문이다. 주행·환승 보행 시간은 모든 구분에서
같다(평일 시간표로 추정). 정의 원본은 [`time-slots.json`](time-slots.json)이고 파이프라인(배차 창·원천 코드), 서버(약속 날짜·시각 →
구분, 표시 문구), 웹(입력 칩·지금 시각 기본값)이 같은 정의를 쓴다. 파일 안의 `vectors`로 서버(Kotlin)와 웹(TS)이 같은 답을 내는지 검사한다.

- **구분 id** = `{요일 유형}-{시간대}`. 요일 유형: `weekday`(평일) · `saturday`(토요일) · `holiday`(일요일·공휴일). 시간대: `morning`(아침,
  ~10시) · `day`(낮, 10~17시) · `evening`(저녁, 17~21시) · `night`(밤, 21시~). 12개. **기본 구분은 `weekday-day`**(평일 낮)이며 T2 이전의
  유일한 기준과 같은 값이다.
- **날짜·시각 → 구분**(방): 시각이 `[from, to)`에 들면 그 시간대(밤은 21:00~다음 날 03:00). 03:00 전의 시각은 **전날 운행일**의 밤이다.
  요일 유형은 운행일로 정한다: 공휴일이거나 일요일 → `holiday`, 토요일 → `saturday`, 그 밖 → `weekday`. 시각이 없으면 낮, 날짜가 없으면 평일.
- **시간대만 고른 방**(`meetingBand`, 시각 없음): 그 시간대이고 운행일은 날짜 그대로다(토요일 밤을 고르면 토요일 밤). 화면에 없는 시각을
  만들어 저장하지 않으려는 것이다. 시각이 있으면 시간대는 시각에서 나오고 서버는 시간대를 따로 저장하지 않는다(함께 온 값이 다르면 400).
- **공휴일**: [`holidays.json`](holidays.json)(관공서 공휴일과 대체공휴일, 출처 포함). 연 1회 갱신한다(우주항공청이 매년 6월 말 다음 해
  월력요항을 발표하면 그 해를 더하고 `coverage.to`를 늘린다. 임시공휴일은 국무회의 의결 뒤). 목록 범위 밖의 날짜는 일요일만 공휴일로 본다.
  서버 테스트는 범위가 끝나기 두 달 전부터 경고를 남긴다(벽시계로 CI를 깨뜨리지 않는다). 외부 키가 필요한 공휴일 API는 쓰지 않는다.
- **배차를 재는 창**(`headwayWindow`, 출발 시각, 양끝 포함): 아침 07~10시, 낮 10~16시(P2b의 평시 창 그대로라 평일 낮 행렬은 T2 전과 바이트가
  같다), 저녁 17~21시, 밤 21~24시. 근거와 측정은 docs/setup/t2-notes.md.
- **표시**: 결과 응답의 `timeBasis.label`("토요일 저녁")을 서버가 만들고 클라이언트는 그대로 쓴다(openapi `TimeBasis`).

## 10. `lt.bin` — 귀갓길 막차 표 (집 역 N × 만날 역 M × 요일 종류 3)

"이 역에서 만나면 각자 몇 시까지 타야 집에 가는가"(#62). 순위에는 쓰지 않고 결과에 덧붙이는 값이다. 계산 규칙과 근거는
[docs/research/last-train-design-fable.md](../docs/research/last-train-design-fable.md)와 [docs/setup/w21-notes.md](../docs/setup/w21-notes.md),
구현은 `shared/schema`의 `LtBinCodec`(형식)과 `pipeline`의 `LastTrain*.kt`(계산), 독립 오라클은 `prototype/last_train.py`다.

- **축은 od.bin과 같은 값·같은 순서다.** 행 = 집 역 = od.bin의 출발역 축(참가자의 출발역이 곧 돌아갈 역이다), 열 = 만날 역 = od.bin의 후보
  축. 그래서 서버는 od.bin에서 쓰는 인덱스로 그대로 찾는다. 축이 다르면 reader는 거부한다(§5 ⑨).
- 리틀 엔디언, 부호 없음. 해시·발행 이름·결정성 규칙은 od.bin과 같다(§4.3, `lt.<해시 앞 16자>.bin`).

### 10.1 헤더 (고정 32바이트)

| 오프셋 | 크기 | 필드 | 값 / 규칙 |
|---|---|---|---|
| 0 | 4 | `magic` | ASCII `BBLT` |
| 4 | 2 | `formatVersion` | u16, 지금 `1` |
| 6 | 2 | `headerSize` | u16, 지금 `32` |
| 8 | 4 | `flags` | u32, 지금 `0`. 0이 아니면 거부 |
| 12 | 4 | `registryVersion` | u32. manifest·od.bin과 같아야 한다 |
| 16 | 4 | `homeCount` N | u32 |
| 20 | 4 | `meetingCount` M | u32 |
| 24 | 8 | `reserved` | u64, `0`이어야 한다 |

### 10.2 본문 (헤더 바로 뒤, 패딩 없음, 이 순서)

집 역 코드 2·N, 만날 역 코드 2·M(둘 다 u16 `codeValue`, 엄격한 오름차순). 이어서 **평일 · 토요일 · 휴일 순서로** 요일 종류마다 세 판이
온다(행 우선: row = 집 역 인덱스, col = 만날 역 인덱스).

| 판 | 크기 | 내용 |
|---|---|---|
| 시각 | 2·N·M | u16. 만날 역에서 타는 시각, **운행일의 분**(03:00에 운행일이 바뀐다. 23:10 = 1390, 다음 날 00:03 = 1443). `0xFFFF` = 없음 |
| 분류 | N·M | u8. `0` 확인 필요, `1` 직행 확정, `2` 여유 시각(갈아타는 길), `3` 여유 시각(열차 한 대, 공식표 대조를 통과하지 못했거나 대조할 공식표가 없는 노선·구간, 또는 부산권 1~4호선처럼 도착 분만 대조한 칸 §12), `4` 출발 예정(열차 한 대, 공식표 대조를 통과했지만 그 분이 만날 역의 계획 도착보다 늦은 계획 출발 분. 세대 5의 부산권 칸에만 있다 §12) |
| 행선지 | 2·N·M | u16 역 코드 값. 열차 한 대로 가는 칸(`1`, `3`, `4`)의 그 열차 종착역. 그 밖은 `0xFFFF` |

총 길이는 정확히 `headerSize + 2N + 2M + 3 × 5NM`바이트다(653 × 127이면 1,245,557). reader가 거부하는 **칸 불변식**:
분류가 `0`이면 시각·행선지가 모두 없음, 아니면 시각이 `1200..1619`(20:00~26:59). 행선지는 분류 `1`·`3`·`4`에 반드시 있고 `0`·`2`에는 없다.
모르는 분류 값은 거부한다. 대각(집 역 = 만날 역)은 분류 `0`이다(파이프라인 불변식).

### 10.3 값의 뜻 (쓰는 쪽의 규칙)

- **시각은 열차의 정체가 증명되는 구간으로만 만든다.** 증명은 두 가지다. ① 열차 번호가 있는 원천의 줄(서울교통공사 1~8호선 S5, 서울교통공사
  공식 파일 S7의 1~9호선): 같은 번호의 줄이 한 열차다. ② 열차 번호 없는 노선의 직행 칸 가운데, 운영사 공식 시간표에서 그 칸의 막차 분과
  행선지를 읽어 적은 표본(`last-train-official.csv`, `last-train.json`의 `exact` 노선)과 우리 계산이 같은 칸: 그 칸 하나만 낸다.
  열차 번호 없는 줄을 이어 만든 열차로만 갈 수 있는 구간이 경로에 끼면 그 칸은 분류 `0`(확인 필요)이다. ②의 칸은 갈아타는 길의 구간으로
  쓰지 않는다. 줄을 잇는 계산은 `last-train.json`의 `rebuild.enabled`로 켜고 끄며 **기본은 꺼짐**이다(꺼져 있어도 ②의 대조와 번호 가린
  채점에는 쓴다). 아래 "열차를 세우는 규칙"의 줄 잇기와 "둘째 원천"의 두 번 계산은 켰을 때의 규칙이다. 근거와 노선을 넓히는 조건은
  [docs/setup/w21-notes.md](../docs/setup/w21-notes.md)의 "시각을 내는 조건".
- **시각은 시간표에서 읽은 실제 이음의 첫 승차 시각에서 원천 여유를 뺀 값이다.** 어림한 값이 아니라, 그 시각에 타면 시간표대로 집 역에
  닿는 열차(들)가 있다. 오차는 이른 쪽으로만 난다(더 늦은 길이 있을 수는 있어도, 보인 시각에 타서 못 가는 일은 시간표상 없다).
- **원천 여유(3분, `sourceMarginSeconds` 180).** 운영사 공식 시간표와 대조를 통과하지 못한 시간표의 열차는 **출발 3분 전까지 타는 것**으로
  계산한다. 원천(TAGO)이 운영사 개정판과 1~2분 다를 수 있기 때문이다: 휴일 9호선에서 TAGO가 운영사 파일보다 역 쌍 225개에서 늦었고
  최대 120초였다(예: 당산 23:50:05 대 23:48:30. 열차 잇기 규칙을 고치기 전 측정으로는 최대 125초). 관측한 최댓값(2분 남짓)에 1분을 더해
  3분으로 잡았다. 대조를 통과한 노선·요일 종류의 열차와 둘째 원천(운영사 파일) 자체의 열차에는 두지 않는다. 발행 게이트는 대조한 모든
  노선에서 "우리가 늦은 최댓값 ≤ 원천 여유"를 확인한다(넘으면 발행하지 않는다).
- **둘째 원천.** 열차코드가 있는 운영사 공식 파일(S7, 서울교통공사 1~9호선 열차운행시각표)이 함께 있는 TAGO 노선(1·3·4·7·8·9호선)은
  표를 두 번 계산한다(TAGO 줄로 다시 이은 열차 / 운영사 파일의 열차). 칸마다 **화면에 더 이르게 보이는 쪽**을 쓰고, 한쪽이라도 길을 찾지
  못하면 확인 필요다. 어느 쪽이 현행 시간표든 보인 시각에 타면 집에 간다.
- **분류 `1`(직행 확정)** 은 열차 한 대로 가고, **타는 줄과 내리는 줄이 모두 대조를 통과한 노선·요일 종류의 것**인 경우다. 화면은 분 단위
  그대로 보인다. 대조는 두 가지다. ① 열차 번호가 있는 서울교통공사 1~8호선(S5)은 발행 때마다 운영사 파일(S7)과 **역 쌍마다 마지막 직행
  출발(초)과 그 출발의 행선지(종착역) 집합**을 견주어, 그 노선·요일 종류의 모든 쌍이 같을 때만 확정이다(하나라도 다르거나 파일이 없으면 그 노선·요일은 원천 여유를 둔 여유
  시각으로 내려간다. 사람이 고르는 목록이 없다). ② 번호 없는 노선은 `data/config/last-train.json`의 `exact`에 적고 운영사 역별 시간표
  표본(`last-train-official.csv`)이 통과해야 한다(지금 신분당선). 9호선은 운영사 파일과 TAGO가 달라 확정에서 뺀다. 직통 열차의 번호 없는
  구간(예: 서울 구간 밖)에서 타거나 내리면 확정이 아니다.
- **분류 `2`·`3`(여유 시각)** 은 화면에서 **10분 단위로 내려** 보인다(반올림은 클라이언트 몫이라 표에는 내리지 않은 분이 들어 있다).
  갈아탈 때마다 `max(10분, 걷는 시간 × 2 + 5분)`을 두고 찾는다. 갈아타는 길은 내린 값이 직행의 보이는 값보다 늦을 때만 직행을 이긴다.
- **분류 `4`(출발 예정)** 는 분 단위 그대로 보이되 **그 사람의 줄에만** 쓴다. 그 분은 열차가 떠나는 계획 시각이라 그 분이 되면 이미
  떠난다. 그래서 탈 수 있는 마지막 순간의 하한이 아니고, "늦어도 나갈 시각"·"전 출발" 요약과 공유 그림에는 넣지 않는다. 약속 시각까지
  떠나는지는 분류 `1`과 같이 판정한다(계획 출발이 약속 시각 이하면 귀갓길에 탈 수 없다). 세대 3·4의 lt.bin에는 없고, 세대 5만 읽는
  서버가 읽는다. 그래서 형식은 1판 그대로다. 서버는 이 분류를 읽을 줄 안다고 밝힌 요청(`lastTrainKinds=scheduled`, openapi)에만
  `kind=scheduled`로 주고, 다른 요청에는 같은 칸을 확인 필요(`check`)로 준다. 이 분류를 모르는 옛 웹이 새 서버와 함께 떠 있는 동안
  (서버 우선 배포, 웹 우선 되돌림) 그 시각을 여유 시각으로 읽지 않게 하려는 것이다.
- **분류 `0`(확인 필요)**: 그 요일 종류에 허용된 노선(`last-train.json`의 `days`) 가운데 열차의 정체가 증명되는 구간만으로는 20:00 이후에
  닿는 길을 찾지 못했다(열차 번호 없는 원천뿐인 노선을 지나야 하는 길 포함).
  "갈 수 없다"는 뜻이 아니다. 요일 종류끼리 시간표를 대신 쓰지 않는다(토요일에 휴일 시간표를 쓰지 않는다).
- **값 없음 표식**: 서울교통공사 공식 파일(S7)과 역별 시간표(S5)는 값이 없는 칸을 `00:00:00`으로 적는다(급행이 지나가기만 하는 역의 도착,
  첫 역의 도착, 마지막 역의 출발). 자정은 `24:00:00`이다. `00:00:00`은 결측으로 읽는다. 자정으로 읽으면 지나가는 역이 정차역이 된다.
- **열차를 세우는 규칙**: 열차 번호가 있는 원천(서울교통공사 1~8호선)은 번호로 묶는다. 번호가 없는 원천은 역별 시간표의 줄을
  "같은 종착역, 종착역 쪽 이웃만, 다음 역에 예상한 시각 ±90초"로 이어 열차를 다시 만든다. 예상 시각은 다음 역 줄에 도착 시각이 있으면
  **도착**(이 역 출발 + 주행 시간), 없으면 출발(이 역 출발 + 역간 시간)이다. 다음 역의 줄은 **이 줄의 출발보다 뒤**여야 한다(대피하느라
  오래 서는 완행의 출발 줄에 뒤따르는 급행을 잇지 않는다). **하나뿐일 때만 잇는다**: ±90초 안에 후보가 둘 이상이면 잇지 않고, 한 줄을
  ±90초 안에서 자기 것이라 할 수 있는 줄이 둘 이상이어도 잇지 않는다. 어느 쪽이 더 가까운지는 근거로 쓰지 않는다(다음 역에서 시작하는
  열차가 통과 급행의 예상 시각에 정확히 놓일 수 있다). **도착 시각이 없는 줄은 그 역에서 시작하는 다른 열차일 수 있다**: 그런 줄로는
  예상 시각 ±5분 안에 같은 종착역의 다른 줄이 없고, ±5분 안에서 그 줄을 자기 것이라 할 다른 줄도 없을 때만 잇는다. 잇지 않은 자리에서
  열차는 끊기고, 끊긴 열차는 이른 쪽으로만 틀린다(그 이음을 넘어가는 승차는 버려진다). **도착 시각이 없는 줄은 정차가 아니다**
  (급행이 지나가기만 하는 역에도 줄이 있다): 그 줄에서는 내릴 수 없고, 열차가 거기서 운행을 시작하는 경우에만 탈 수 있다.

## 11. `rg.bin` — 사람별 경로의 노선 그래프 (#120)

"이 사람은 어느 노선을 타고 어디서 갈아타는가"를 서버가 **요청할 때 다시 계산**하는 데 쓰는 그래프다. 경로 자체는 저장하지 않는다
([ADR-0002](../docs/adr/0002-routes-on-request.md)). 순위·시간·환승 수에는 쓰지 않고 결과 화면의 막대에만 붙는다. 구현은 `shared/schema`의
`RouteGraphCodec`(형식), `shared/core`의 `RouteSearch`(계산), `pipeline`의 `RouteGraphStage.kt`(만들기와 게이트)다.

- **od.bin을 만든 그래프와 같은 노드·간선이다.** 노드 = (역, 계통), 간선은 타고 가는 간선(주행)과 갈아타는 간선(같은 역 안에서 걷기 +
  다음 열차 대기, 환승 1회)이다. 구분(§9)마다 다른 것은 계통별 타기 대기(배차/2)뿐이라 대기를 뺀 간선과 구분별 대기표를 둔다.
- **발행 게이트:** 파이프라인은 이 파일의 바이트를 다시 읽어 `RouteSearch`로 **모든 구분 × 모든 출발역 × 모든 후보역**의 최단
  (시간, 환승)을 계산하고, od.bin·구분 행렬의 칸과 하나라도 다르면 발행하지 않는다. 같은 검사를 CI가 커밋된 dev 산출물로 한다
  (`RouteGraphCommittedDataTest`). 그래서 서버가 이 그래프로 낸 경로는 od의 시간과 어긋나지 않는다.
- 리틀 엔디언, 부호 없음. 해시·발행 이름·결정성 규칙은 od.bin과 같다(§4.3, `rg.<해시 앞 16자>.bin`).

### 11.1 헤더 (고정 32바이트)

| 오프셋 | 크기 | 필드 | 값 / 규칙 |
|---|---|---|---|
| 0 | 4 | `magic` | ASCII `BBRG` |
| 4 | 2 | `formatVersion` | u16, 발행본 `1`, 권역 미리 보기 `2`(§11.4) |
| 6 | 2 | `headerSize` | u16, 지금 `32` |
| 8 | 4 | `flags` | u32, 지금 `0`. 0이 아니면 거부 |
| 12 | 4 | `registryVersion` | u32. manifest·od.bin과 같아야 한다 |
| 16 | 4 | `nodeCount` V | u32, 1..65535 |
| 20 | 4 | `edgeCount` E | u32 |
| 24 | 2 | `lineCount` L | u16, 1..255 |

### 11.2 본문 (헤더 바로 뒤, 패딩 없음, 이 순서)

| 구간 | 크기 | 내용 |
|---|---|---|
| 노선 이름 | L × (1 + n) | u8 바이트 길이 n(1..255) + UTF-8. 화면 표시 노선 이름(예: `2호선`, `수인분당선`, `공항철도`). 겹치지 않는다. 웹 노선 색표(`web/src/lib/stations/lines.ts`)의 키와 같은 말이다 |
| 계통의 노선 | S | u8 노선 이름 색인 |
| 노드 | 3·V | 노드마다 u16 역 `codeValue` + u8 계통 색인 |
| 간선 시작 위치 | 4·(V+1) | u32. 노드 `v`의 간선은 `[start[v], start[v+1])`. 처음은 0, 끝은 E, 줄지 않는다 |
| 간선 | 5·E | 간선마다 u16 도착 노드 + u16 초(대기를 뺀 시간) + u8 대기 계통(`0xFF` = 타고 가는 간선) |
| 구분별 대기표 | 2·12·S | u16 초. 구분 순서는 요일 종류(평일·토요일·휴일) 안에서 시간대(아침·낮·저녁·밤)다(`TimeSlot.ALL`, §9의 id로 `weekday-morning`, `weekday-day`, …, `holiday-night`). 그 안은 계통 색인 순서 |

총 길이는 정확히 읽은 만큼이어야 한다(남거나 모자라면 거부). 지금 데이터는 노드 966, 간선 2,896, 약 22.6KB다.
형식 1에서 reader가 거부하는 불변식: 색인이 범위 안, **타고 가는 간선은 1초 이상**, 갈아타는 간선의 걷기는 0초 이상(같은 승강장이면 0초,
대기만 더한다), **갈아타는 간선은 같은 역의 두 노드만 잇는다**, 대기는 1..65534초.

### 11.3 값의 뜻 (읽는 쪽의 규칙)

- 간선 시간: 타고 가는 간선은 초 그대로, 갈아타는 간선은 초 + 그 구분의 대기 계통 대기. 출발역에서는 그 역의 모든 노드에서 그 노드
  계통의 대기만큼 기다리고 시작한다. 도착역은 그 역의 노드 가운데 가장 빠른 것이다. 이것이 od.bin 한 칸의 (시간, 환승)이다.
- **화면에 보이는 경로**는 최단 경로가 아닐 수 있다: 최단 시간보다 **120초**(`DISPLAY_ROUTE_SLACK_SECONDS`) 이내로 더 걸리는 경로
  가운데 환승이 가장 적은 것, 같은 환승 수면 더 빠른 것이다. 동률은 (시간, 노드 색인) 순서로 먼저 찾은 쪽이다. 표시 전용이라
  순위·시간·환승 수는 그대로 od.bin의 값이다.
- 구간 시간(대기·주행)은 배차/2 평균 대기로 만든 모델 값이라 화면에 숫자로 쓰지 않는다(막대 길이 비율에만 쓴다).
- 한 역에서 타지 않고 두 번 갈아타는 경로(지금 데이터는 김포공항 공항철도 → 5호선 승강장 → 서해선뿐)는 화면에서 환승 한 번으로 합친다.

### 11.4 권역 그래프 형식 2 (#180, 발행 전 검증)

헤더와 본문 배치는 형식 1과 같고 `formatVersion`은 `2`다.

- 다른 역 코드의 노드를 잇는 대기 계통 간선은 **외부 도보 연결**이다. 걸리는 시간은
  1..65534초이고 대기 계통 색인은 도착 노드의 계통이어야 한다. 방향마다 간선을
  명시한다. 이미 열차를 탄 경로가 이 간선으로 갈아타면 도보와 다음 열차 대기 및
  환승 1회를 더한다. 첫 승차 전과 마지막 하차 후의 외부 도보에는 타지 않은 계통의
  대기와 환승을 더하지 않는다. 도보만으로 이동하면 도보 시간과 환승 0회다.
  부산 파이프라인 입력에서는 역 코드가 외부 도보 쌍 하나에만 속할 수 있어
  외부 도보 연결의 연쇄를 허용하지 않는다.
- 대기표의 `0xFFFF`는 해당 구분에 그 계통의 배차를 모른다는 뜻이다. 출발·환승
  때 그 계통을 선택할 수 없다. 다른 계통으로 계산할 수 있는 칸은 계산한다.
  출발역과 외부 도보로 닿는 역에 이용 가능한 계통이 없으면 그 구분의 출발 지원이 없고 OD는 도달 불가
  표식(§4)을 쓴다. 해당 구분의 다른 요일·시간대 배차로 대체하지 않는다.
- 현 경로 응답의 승차 구간 목록은 코드가 다른 역 사이의 도보를 설명할 수 없다.
  외부 도보가 포함된 표시 경로는 도보 구간의 응답 계약이 생기기 전까지 생략한다.
  OD와 최단 경로 계산에는 걷는 시간을 포함한다.
- 기존 manifest 세대 1~4의 로더는 형식 1을 요구한다. 향후 권역 발행은 운영자
  승인 후 별도 포인터 `regional/manifest.v5.json`과 파일 키
  `regional/versions/<dataVersion>/…`를 사용한다. 기존 포인터와 `versions/`를
  유지하므로 옛 서버의 포인터 읽기와 `/v1/data` 직접 조회는 권역 파일을 발견하지
  못한다. 형식 2의 오프라인 미리 보기는 이 포인터와 파일을 쓰지 않는다.

## 12. 권역 데이터의 manifest 5세대

- `regional/manifest.v5.json`만 `schemaVersion=5`, `minClientSchema=5`다.
  모든 파일 키는 `regional/versions/<dataVersion>/<파일>` 형식이다. 별도 포인터
  한 개가 같은 버전의 레지스트리·행렬·그래프를 가리킨다. 세대 5는
  `stations.json` 2판과 rg.bin 2판을 요구한다. 후보·od.bin·lt.bin의 형식은 1판이다.
  권역별로 막차까지 검증된 칸만 시각을 넣는다.
- 부산권 막차 칸([ADR-0010](../docs/adr/0010-busan-direct-last-trains.md))은 열차 한 대로 가는 직행만 시각을 넣는다.
  1~4호선은 B1 열차가 만날 역에 **도착하는 분**을 분류 `3`(여유 시각)으로 넣는다. 그 분은 운영사 표(H1)와 같은
  계획상 하한이다. 동해선은 TAGO의 출발 분을 넣는다. 그 출발은 운영사 표(K2)와 초까지 같다. 그 분이 TAGO의 계획 도착
  이하면 분류 `1`(직행 확정), 계획 도착보다 늦으면(`:00`초 출발, 도착은 30초 앞) 분류 `4`(출발 예정), TAGO에 도착이 없으면 분류 `0`이다.
  행선지는 그 열차의 종착역이다. 운영사 표와 다른 칸, 막차가 만날 역에서 출발하는 시발역 칸(1~4호선, 동해선), 갈아타는 길,
  동해선 토요일, 부산김해경전철은 분류 `0`이다. 두 노선이 모두 직행인 칸은 분류 `4`가 아닌 쪽(승차 하한)을 먼저 고르고,
  그다음 화면에 늦게 보이는 쪽을 넣는다.
  권역 사이 칸은 분류 `0`이고, 수도권 칸은 수도권 표의 값과 바이트까지 같다. 대조와 끄는 조건은
  [data/README](../data/README.md#부산권-직행-막차-대조-180)에 있다.
- `regionCoverage`는 OD 출발역이 있는 권역 각각에 구분 12개의 상태를 담는다.
  값의 키는 `weekday-day` 같은 구분 id다. 구분 값의 세 필드는 필수다.
  `missingServices`는 배차를 확인하지 못한 계통의 표시 이름(중복 없이 오름차순),
  `unsupportedOrigins`는 해당 계통을 빼면 승차할 수 없는 출발역 코드(중복 없이
  오름차순)다. `available`은 배차를 확인한 그래프가 연결되고 지원 출발역이 두 곳
  이상일 때만 `true`다. 다른 권역끼리의 칸과 미지원 출발역·구분의 칸은 도달 불가다.
  서버는 부산권의 미지원 구분을 평일 낮으로 대체하지 않는다.
- 레지스트리 2판에는 지원 권역(`capital`·`busan`)의 역만 둔다. 1판에 있는 다른 권역의 역(대구·대전·광주 등)은 빠진다.
  빠진 역은 그래프 노드·OD 축·남은 역의 `replacedBy`에 없어야 한다.
- 서버는 설정 `REGIONAL_ARTIFACTS=true`로 이 포인터를 명시적으로 선택한다.
  포인터가 없거나 기본 파일 검증이 실패하면 기동이 실패한다. 기본 설정의 서버는
  기존 포인터와 `versions/`를 읽는다. 권역 파일의 저장·선택은 운영자가 발행을
  승인한 뒤 진행한다.
- 수도권 투영과 SEO 값은 ADR-0008의 발행 조건을 충족해야 한다.
